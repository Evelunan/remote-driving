# 视频性能测量与改造记录

当前保留 aiortc、OpenCV 和 PyQt 路线，没有切换媒体后端或启用硬件编解码。下列结果按测量边界分别报告，不能相互替代。B11–B13 的描述保留当时的进度；正式入口、车端进程隔离和主视角失效联动已分别在 B14–B16 完成，最新状态见 [实施记录](refactoring-progress.zh-CN.md)。

## B11：驾驶端帧缓存

旧实现每次 `FrameBuffer.get()` 都深复制图像，显示组件在复制后才根据帧 ID 丢弃重复帧。新实现由生产者在发布时复制一次，缓存持有只读快照，轮询仅取得引用和版本。复制在元数据锁外完成，读者持有的旧快照不会被下一帧覆盖。会话代次在复制前后均检查，关闭或重连后的旧回调不能恢复旧画面。

显示时间调试文字改为可选 Qt 覆盖层，默认关闭，不再原地修改像素。没有新接收帧达到阈值时清除画面和 FPS/尺寸，显示“接收画面已过期”；新帧到达后恢复。此处依据本地接收时间，尚不能识别发送端把旧相机图像重复编码成新帧的情况，采集源新鲜度仍需继续改造。

### 复现

在已安装工作区依赖的 Python 3.12 环境执行：

```bash
.venv/bin/python scripts/benchmark_frame_buffer.py --output /tmp/frame-buffer-comparison.json
.venv/bin/python -m pytest -q tests/test_frame_cache.py
```

基准使用固定随机种子 42，一路 1080×720、三路 640×480 的 BGR 图像；输入 30 FPS，轮询 200 Hz，逻辑时长 3 秒，预热后重复 5 次。使用逻辑调度而非 sleep，统计此工作负载消耗的进程 CPU 和墙钟时间，不将逻辑秒数当作实际运行时长。NumPy 数组的 `copy()` 计数记录复制次数和载荷字节；不代表硬件内存总线流量。

改造前代码完整保存于 [基准快照](../benchmarks/baselines/frame_buffer_before_b11.py)，来源为提交 `9ec4447`。报告记录新旧代码 SHA256、Python、NumPy 和操作系统版本。[改造前报告](../benchmarks/results/frame-buffer-b11-before.json) 在改写实现前生成；[对比报告](../benchmarks/results/frame-buffer-b11-comparison.json) 在同一主机、同一脚本内依次运行新旧实现。

本次环境为 WSL2/Linux、Python 3.12.16、NumPy 2.4.4。CPU/墙钟数值受宿主机负载影响；没有调用相机、编码器、网络、Qt 或 GPU。

| 指标，每 3 秒逻辑负载 | 改造前 | 改造后 |
| --- | ---: | ---: |
| 发布帧数 / 不重复显示帧数 | 360 / 360 | 360 / 360 |
| 图像复制次数 | 2,400 | 360 |
| 复制载荷字节 | 3,058,560,000 | 458,784,000 |
| CPU 中位耗时 | 128.99 ms | 22.13 ms |
| 墙钟中位耗时 | 128.98 ms | 22.12 ms |

同一工作负载复制载荷减少 **85%**，缓存部分 CPU 耗时约减少 **82.8%**。不能据此宣称整体视频帧率、端到端延迟或编码性能改善相同比例。

### 正确性与剩余验证

回归覆盖输入数组复用、快照只读与保留、复制期间关闭会话、过期边界、非法图像，以及 Qt offscreen 显示/过期/恢复。原有可选 OpenGL 组件也改为消费快照、只上传新帧、分辨率改变时重新分配纹理，使用 BGR 和单字节行对齐；测试只模拟 GL 调用验证契约，默认显示路径仍为普通 PyQt 组件，真实 GPU/桌面验收待完成。

后续须完成接收端与信令关闭重连，并补充单路/四路完整媒体链路的 CPU、RSS、事件循环延迟、编码/接收 FPS、首帧/重连耗时和网络统计。真实相机、TURN、受限网络、硬件编解码和跨主机端到端延迟需在目标设备上验收。

## B12：采集与订阅生命周期

采集源现在保留一张最新的只读图像及其序号、主机采集完成时间；相机线程用有界通知唤醒发布协程，序号未变时不发布。通知队列最多保留一个待执行回调，不把每张图像捕获到回调中积压。USB 读帧失败会使源失效，线程异常会传给应用监督任务；合成相机使用固定种子和序号生成图像，便于复现。

每个 WebRTC peer 使用独立轨道，关闭或替换某个 peer 不停止其他 peer 或底层相机。轨道只发送未消费且未过期的采集帧，按相机目标 FPS 控制上限，PTS 使用采集时间差和 90 kHz 时基。没有新图像时等待新采集事件，停止订阅会唤醒等待者并抛出 `MediaStreamError`；不再发送黑色占位帧或给旧图像分配新 PTS。订阅者各自创建 AV 帧，避免编码器修改 AV 元数据时相互影响。

相机适配器将打开、读帧和释放句柄放在同一个线程；移除了忙等和固定三秒预热。OpenCV 适配器可以接收设备索引或稳定路径，记录后端及实际协商参数，保留实际图像尺寸，不静默缩放到请求尺寸。当前正式 CLI 的旧 VID/PID 配置仍待迁移，不能仅凭适配器支持路径就宣称新配置已全部生效。

`MultiCameraManager.stop()` 现在是需要等待的异步方法：停止接收通知，等待正在进行的启动，取消并等待发布任务，再关闭相机线程。驱动调用若一直阻塞，会明确报出线程仍存活；Python 线程不能强行终止硬件驱动，媒体进程隔离和目标设备验收仍待完成。推流端关闭会取消并等待自身连接任务，断线先清理 peer/订阅再重连，关闭后不自动重连。

验证命令：

```bash
.venv/bin/python -m pytest -q tests/test_video_sources.py
```

覆盖无帧/过期/重复帧、10/60 FPS 上限、采集 PTS、慢订阅者只取最新帧、独立订阅与替换、关闭唤醒、重复启动关闭、相机启动失败和取消回滚、采集异常、稳定路径及句柄线程归属。真实 aiortc 测试使用合成图像、无 STUN/TURN、仅 `127.0.0.1` 候选，验证两个接收者同时收流，其中一个退出和重连不影响另一个。

这里证明的是软件生命周期与本机功能，不是硬件速度提升或整条视频链路的性能验收。主机采集完成时间不是传感器曝光时间，也不能与另一主机的单调时钟直接相减。信令客户端认证、驾驶端接收任务/Qt 生命周期、统一入口配置、媒体进程隔离和网络下的画面年龄诊断仍待后续实现。

## B13：认证会话与接收端关闭

两端采用共享的 `MediaSession` 与 `SignalingClient`，管理认证房间确认、重连、peer、接收任务和清理。当前连接身份在关闭前失效，晚到的解码结果不会交给下一代会话；关闭等待全部任务，停止后不重连。真实 WSS + WebRTC 回环验证了车辆、驾驶端和查看者同时工作、信令断线恢复、驾驶端退出后查看者继续收流。

Qt 工作线程使用受管理的 asyncio 生命周期，停止请求立即返回；主窗口等旧线程结束后才重连、注销或关闭，并以代次过滤旧状态信号和帧。界面分别显示认证加入、媒体握手、首帧与主画面过期状态。offscreen 测试证明旧线程关闭期间 GUI 定时器继续运行，但真实桌面、GPU 和控制/媒体进程隔离仍待验收。

视频发布方向现在受服务端角色约束，每房间只允许一个车辆发布者；普通接收者不能冒充车辆提供画面。证书、房间拒绝、重定向防令牌泄露和 DEBUG 日志脱敏均有本地回归。复现新增覆盖：

```bash
.venv/bin/python -m pytest -q tests/test_signaling_client.py tests/test_media_sessions.py tests/test_signaling_authorization.py
```

媒体路径已从统一配置读取网络、凭据和部分显示参数；正式控制入口以及其余旧 UI/相机配置仍待后续批次迁移。全链路性能测量、跨主机画面年龄和真实设备验收尚未完成。


## B18：真实软件媒体链路基线

新增 [测量入口](../scripts/benchmark_media.py) 和 [关联探针](../scripts/media_probe.py)。工具执行实际 `MultiCameraManager`、`WebRTCStreamer`、`WebRTCReceiver`、`FrameBuffer` 与 `MultiVideoWidget`，使用认证 WSS、WebRTC 编解码与传输、QUIC 控制客户端及模拟底盘。主画面实际 Qt paint 回调提供控制就绪证据；没有用假的视频就绪事件替代显示链路。

### 固定负载与复现

```bash
.venv/bin/python scripts/benchmark_media.py --views 1 --seconds 10 --label baseline --output /tmp/media-one.json
.venv/bin/python scripts/benchmark_media.py --views 4 --seconds 10 --label baseline --output /tmp/media-four.json
.venv/bin/python -m pytest -q tests/test_media_measurement.py
```

默认一路前视 1080×720，另外三路 640×480；均为 30 FPS，单个订阅者，Qt 1280×720 窗口、16 ms 刷新。固定种子 42 派生各相机种子，用移动的平滑纹理构造合成场景，另外支持 `--scene moving-flat`。负载不代表真实道路内容的压缩复杂度，必须保留场景、尺寸、编码器和码率记录后才能比较。`--profile small` 只用于工具回归，不能与正式尺寸结果混比。

每次运行包括初次建连、2 秒预热、10 秒稳定阶段、主动断开车辆信令、等待新发布身份的四路画面与新控制租约、再次预热及 10 秒恢复阶段。单路与四路交替重复三轮，测量时不并行运行其他回归或基准。`--warmup` 和 `--seconds` 可显式调整。工具不会选择实际相机、USB、ROS 或串口；ICE 限定并检查实际候选为 127.0.0.1，未配置 STUN/TURN。

### 时间与统计口径

合成图像携带 128×128 像素的 64 位黑白方块标记（每格 16×16）：魔数、视角、32 位采集序号和 CRC16。标记经过真实有损编解码后再从接收像素读取，关联同一帧的采集、编码、解码、缓存和绘制时间。接收标记损坏、重复、顺序异常、缺少处理边界或超出探针容量时，不给出有效测量结论。初版 64×64 标记在四路重复实验中有一次识别失败，整轮结果已废弃；增强标记后重新采集完整基线，不通过剔除坏帧得到通过结论。解码相关对象只记录时间与序号，不额外保存图像；探针有 60,000 条记录上限。

| 测量 | 边界及限制 |
| --- | --- |
| 采集到编码输入 | 相机 `_read()` 返回后的主机单调时间，到 AV 帧交给编码器；包含发布调度、限帧等待和 BGR→AV 封装 |
| 编码队列 / 编码函数 | 进入线程池前到开始编码，以及编码函数本身；编码函数包含颜色转换和分包工作 |
| 编码结束到开始解码 | 包含 RTP 发送、回环传输、接收重组、抖动缓冲及解码线程排队，不能全部归因于网络 |
| 解码 / BGR 转换 / 缓存 | 原生解码调用、接收 AV 帧转 BGR、标记识别和缓存发布分别记录 |
| 缓存到渲染 / Qt 缩放 / paint | 最新帧等待 UI 轮询、缩放与 QPixmap 构造，以及 Qt paint 完成；不是显示器出光时刻 |
| FPS | 采集、编码输入、编码输出、解码输出、回调和唯一帧绘制分别计数，保留零值秒和末尾不足一秒的实际时长 |
| 延迟 | 同一帧两个单调时间相减，输出样本数、P50/P95/P99/max；空样本输出 null，零耗时不丢弃 |
| 冻结 | 绘制间隔包含窗口两端，整个窗口无帧时仍计入整个窗口长度；报告超过 500 ms 的间隔数量 |
| 资源与调度 | 整个测量进程的 CPU、Linux RSS、Python/原生线程数、后台 asyncio 和 GUI 定时器延迟；100% CPU 表示占用一个逻辑核 |
| WebRTC | 原始 getStats 每秒保留，阶段统计 RTP 载荷码率、丢包、90 kHz 时基抖动和 RTCP RTT；RTT 不等于单向画面延迟 |
| 控制 | 同时运行 50 Hz 控制客户端，记录采样到模拟控制器调用返回、采样到执行 ACK；均不表示真实底盘运动或停车 |

全链路时间包含探针和标记识别开销，标记识别单独报告。阶段 CPU 不包含报告汇总和 JSON 写盘；RSS 包含探针、合成纹理和所有进程内组件，增长不能直接判定为应用泄漏。接口埋点只在工具进程临时替换并在退出时恢复，绑定 aiortc 1.14.0；版本变化必须先审查埋点。统计校准覆盖实际 VP8 有损往返、损坏标记拒绝、零帧窗口、已知时间差和异常退出后恢复埋点；四路回环测量也进入回归。

### 结果边界与后续优化

本批建立优化前基线，没有据此更换媒体后端或硬件编码器。报告保存源文件哈希、Git 状态、环境、CPU 型号、实际编码器与线程数，供下一批在相同条件下比较。这里将服务端、车辆媒体、驾驶接收和控制循环放在一个后台线程，Qt 位于主线程，以同一进程单调时钟做精确关联；这不是正式车端的独立进程部署。车端进程隔离的资源开销、实机摄像头曝光到显示器延迟、GPU、TURN、弱网与长时间重连仍须各自测量。

### 本机三轮结果

环境：Intel Core i7-11800H、16 个逻辑核、WSL2/Linux、Python 3.12.16；实际协商 VP8，PyAV 的 libvpx 软件编码，前视编码器 2 线程。以下是三轮稳定阶段统计的中位数；P50/P95/P99 为各轮相应分位数的中位数，没有将不同轮次的帧混合后重新计算。

| 指标 | 单路前视 | 四路负载中的前视 |
| --- | ---: | ---: |
| 绘制 FPS | 28.88 | 29.00 |
| 采集完成→Qt paint P50（ms） | 69.52 | 73.81 |
| 采集完成→Qt paint P95（ms） | 87.96 | 91.57 |
| 采集完成→Qt paint P99（ms） | 93.13 | 95.40 |
| 整个进程 CPU（一个逻辑核 = 100%） | 55.33 | 121.60 |
| 整个进程 RSS 中位数（MiB） | 272.25 | 431.60 |
| 控制采样→模拟提交 P99（ms） | 13.18 | 17.56 |
| 控制采样→ACK P99（ms） | 14.60 | 20.49 |
| 前视首帧（ms） | 129.21 | 152.75 |
| 断开信令→全部视角新来源 paint（ms） | 204.74 | 232.48 |
| 断开信令→新控制租约就绪（ms） | 760.28 | 785.74 |

四路前视的阶段 P95：采集到编码输入约 32.55 ms，编码函数约 8.64 ms，编码结束到解码开始约 39.41 ms，缓存到 UI 渲染约 14.77 ms，Qt 缩放/QPixmap 约 0.91 ms。这些阶段分位数不能相加代替端到端分位数。标记识别 P95 约 0.15 ms。下一步先检查编码前节拍与中间缓冲；没有证据将 Qt 缩放认定为本次主要瓶颈。

重连后的 RSS 高于首个稳定阶段，当前短时记录不能判断是分配器保留、编解码缓存还是泄漏，需补充长期重复重连测试。跨轮前视画面 P95 范围：单路 86.97–88.91 ms，四路 91.49–92.79 ms。
