# 四路视频传输与显示改进决策

**本轮采纳的 7 项已经完成，2 项暂缓。** 当前局域网配置使用前、后、左、右四个摄像头，各自采集和编码，通过一个 WebRTC 连接的四条视频轨道传输。驾驶端各轨道独立解码，共用接收线程完成 BGR 转换和缓存发布。四个控件在 Qt 主线程绘制，前视是默认主视角。[车辆配置](../configs/vehicle.lan.yaml) · [车端推流](../apps/vehicle/src/rd_vehicle/infrastructure/streams/webrtc_streamer.py) · [驾驶端接收](../apps/driving/src/rd_driving/infrastructure/video/webrtc_reciver.py)

## 采纳决定与优先级

| 优先级 | 原编号与方案 | 决定与理由 | 实施结果或复议条件 |
| --- | --- | --- | --- |
| P0 | 3 · 主画面新鲜度 | 已完成。链路积压时仍可能持续播放旧帧，正常 FPS 无法证明画面足够新。 | 按已绘制的主帧检查接收时间、采集年龄上界和来源，估算缺失或过期时更新视频状态。 |
| P1 | 1 · 单摄故障隔离 | 已完成。单个摄像头故障时，健康视角仍可观看。 | 对故障摄像头及其复制视角清除旧帧，单独重试。其他摄像头继续推流。控制租约按控制链路状态续期。 |
| P1 | 8 · 绘制帧率与画面年龄 | 已完成。旧控件可在一次实际绘制前累计三次 FPS。 | 只对完成绘制的唯一帧计数。面板显示“当前画面年龄”，从已绘制帧的保守采集时间估算，时间未知时显示缺省值。 |
| P1 | 5 · 新帧通知与合并刷新 | 已完成。原四路回环基准中，前视写入缓存到开始渲染的 P95 为 14.77 ms，接近一个轮询周期。 | 四路共用一个待处理的 Qt 通知，每次取各自最新帧。新帧通知之外，界面定时器分别检查画面与遥测过期，断流也能清除旧状态。 |
| P2 | 7 · 布局切换时保留控件 | 已完成。旧容器释放后，再次访问显示控件会出错。 | 前视主导和四宫格共用四个控件及其边框。切换只调整网格位置，已有画面继续显示，重绘旧帧不会刷新画面有效期。 |
| P2 | 6 · 单路控件直接绘制 | 已完成。旧控件为每个提交帧先缩放并生成 QPixmap，包括尚未显示就被替换的帧。 | 自定义 QWidget 持有最新帧，到 paintEvent 时由 QPainter 等比绘制 QImage。绘制完成后按帧编号通知上层。 |
| P2 | 9 · 常驻视角名称 | 已完成。两种布局中的位置不同，驾驶员需要直接辨认每幅画面。 | 四个视角名称固定在各窗口左上角。等待或过期时，名称变色，中央显示状态文字。 |
| P3 | 4 · 将 BGR 转换和缓存复制移出接收线程 | 暂缓。原四路基准的前视两阶段 P95 分别为 1.75 ms、0.30 ms。后台处理会增加线程交接与重连清理成本。 | 软件负载下若出现已解码帧积压，且主画面年龄 P99 同时上升，再评估每路仅保留一个待处理帧的后台方案。 |
| P3 | 2 · 单条轨道独立恢复 | 暂缓。每路单建连接会增加协商和维护成本，四路仍共享车辆上行链路。 | 若在健康连接上复现单轨结束导致其余三路中断，优先评估在同一连接内恢复该轨道。 |

## 故障后界面和控制的行为

| 情况 | 驾驶端画面 | 控制授权 |
| --- | --- | --- |
| 任一辅助摄像头短时没有新帧 | 该窗口按接收超时提示过期，健康窗口继续刷新 | 保持当前租约 |
| 主摄超过采集超时，或任一采集线程明确报错 | 故障相机单独重试，其他视角继续显示 | 保持当前租约，可继续发送转向、油门和制动 |
| 主画面持续绘制，但采集年龄超过预算或无法确定 | 仍可观察收到的画面。年龄未知时面板显示缺省值 | 控制按原会话继续 |
| 整条媒体链路中断，再次收帧后主画面持续滞后 | 给现有连接恢复时间。超过恢复窗口仍收到可确认过旧的主帧时，驾驶端重建媒体连接 | 视频重连期间继续发送控制并接收执行确认 |

主视角接收超时和车辆主摄采集超时默认均为 500 ms。主画面采集年龄有独立的 300 ms 软件预算。跨端时钟探测半程超过 50 ms、锚点超过 5 s 或来源无法确定时，画面标记为过期或时间未知。摄像头采集时间取自驱动读取返回时刻。[授权与时钟边界](video-safety.zh-CN.md) · [采集监控](../apps/vehicle/src/rd_vehicle/application/multi_camera_manager.py)

## 软件验证

### VP8 组帧与 PyAV 采集格式对照

四路合成视频在同一台 Ubuntu 主机上用实际 WebRTC 回环传输，前视 1080×720，其余三路 640×480，均为 30 FPS。每种接收路径运行两轮，每轮稳定播放采样 5 秒。表中延迟取两轮前视 P95 的中位数。

| 稳定播放指标 | 默认组帧 | 完整 VP8 帧直接送解码 |
| --- | ---: | ---: |
| RTP 组帧缓冲收到该帧最后一个包到组帧完成 | 52.07 ms | 0.03 ms |
| 组帧完成到开始解码 | 1.37 ms | 1.25 ms |
| 采集完成到 Qt 离屏绘制 | 85.26 ms | 46.16 ms |

四路在每轮均绘制约 30 FPS。开启低延迟组帧后，四路丢包抖动和媒体断流恢复模拟均通过，画面授权仍按原有新鲜度和来源规则运行。

真实 USB 相机另做了发送端对照。前视实际协商为 1280×720，其余三路为 640×480，摄像头的 MJPEG 均解码为 `yuvj422p`。一轮 5 秒的采集加 VP8 编码测试中，BGR 路径约占单核 101%，YUV420P 路径约占单核 118%，两者都编码约 30 FPS/路。当前保留 BGR 默认值。

现有系统 FFmpeg 可用本机 GPU 完成 VA-API H.264 编码。两轮各编码 180 帧 720p30 合成视频，目标 750 kbit/s，包含颜色转换和 GPU 上传。VA-API 的 CPU 总时间约 0.34 秒，libx264 约 1.67 秒。该探测未接入正式 WebRTC 链路。项目 PyAV 环境的 QSV 编码器在本机初始化失败。到 192.168.3.7 的真实端到端延迟及目标机原生绘制仍需实测。

### 单摄 720p60 的帧率和画面年龄

11 月 22 日 23:04 的车辆日志显示，前摄请求 1280×720 MJPG、60 FPS，同时向后、左、右提供复制视角。这会从同一摄像头读取一次，向一个驾驶端发送四条各自编码的 720p 轨道。使用 `camera_fallback_source: null` 并只配置前摄时，车辆只发布前视。配置在启动时读取。23:20 和 23:22 启动后的车辆日志中，每 10 秒实际读回约 298–299 帧，即 **29.7–29.9 FPS**。这已限制驾驶端能显示的新帧数。

本项目使用的 OpenCV 4.13.0 在 DirectShow 下根据请求的帧间隔计算 `CAP_PROP_FPS`。例如请求 60 时可读到 60.00024，即使实际每秒只读回 30 帧。每次打开摄像头后，首个 10 秒窗口以 `INFO` 记录实际读回帧率 `read_fps`，后续窗口以 `DEBUG` 记录。`in_read_pct` 表示采集线程在读取函数（包含设备等待和图像取回）中度过的时间，占该窗口墙钟时间的百分比。驾驶端面板 FPS 则按完成绘制的唯一帧计算。[OpenCV DirectShow 实现](https://github.com/opencv/opencv/blob/4.13.0/modules/videoio/src/cap_dshow.cpp#L1357-L1368)

Windows 合成对照使用一个按 60 Hz 供帧的 1280×720 移动色块源、真实 WebRTC 本机回环和 Qt 离屏绘制，每组记录 7 秒。表中四项 FPS 均取前视，画面年龄是完成绘制时按跨端时钟估算的采集年龄。两行使用相同的采集与显示代码，仅改变发送轨道数。

| 发布方式 | 实际读回 FPS | 进入编码器 FPS | 解码后接收 FPS | 实际绘制 FPS | 绘制时年龄 P50 / P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 一摄四轨 | 59.92 | 43.04 | 42.47 | 42.47 | 109 / 126 ms |
| 一摄一轨 | 60.00 | 60.00 | 59.85 | 59.85 | 31 / 47 ms |

这个对照说明四次编解码会影响流畅度，也表明当前软件链路在这一简单场景能显示接近 60 FPS。另有四轨尝试出现校时数据缺失或退出超时，表中仅列同一移动色块场景中完整结束的一对结果。现场摄像头的 100–200 ms 仍缺少分阶段时间记录。针对 Windows 已修复采集定时累积误差、同一时钟刻度的两次读回被误判为相机故障，以及 DirectShow 设置 FPS 后未把 MJPG 与尺寸一并提交的问题。后者的效果尚待新启动的设备会话确认。

### 四路 30 FPS 的版本对照

同机 Ubuntu/WSL 车辆分进程基准比较了 `5953e4e` 与 `820f1f0`。前视为 1080×720，其余三路为 640×480，各路 30 FPS。每版运行四次，正常播放与重连后各测 10 秒。两组新旧配对都通过完整性和控制授权检查。另两组新版在测量窗口内发生撤权，完整记录保留在结果文件中，配对统计仅使用两侧均有效的组。此前共进程预跑存在水印识别错误，也已单列。[逐轮数据与运行参数](../benchmarks/results/video-display-four-view-ab.json)

| 稳定播放指标（有效配对中位数） | 优化前 | 优化后 |
| --- | ---: | ---: |
| 前视写入缓存到界面取帧 P95 | 14.68 ms | 0.66 ms |
| 前视从合成采集完成到 Qt 绘制 P95 | 67.35 ms | 62.45 ms |
| 前视实际绘制 FPS | 29.83 | 29.82 |
| 全部测量进程 CPU（单核为 100%） | 178.45% | 164.70% |

稳定播放时，界面等待少了约 14 ms，整条链路的 P95 只少了约 5 ms。重连后，整条链路 P95 从 79.12 ms 变为 88.88 ms。各轮 CPU 波动明显。两组有效配对只能支持界面等待缩短，尚不足以证明整体延迟、卡顿或 CPU 在现场持续改善。

### 四控件离屏对照

Windows Qt 离屏对照使用四路 1280×720 合成 BGR 图像，后台线程按每路 30 FPS 发布，窗口尺寸为 1280×720。每个阶段预热 10 帧，再取 100 个实际绘制的前视帧。下表记录单次运行的 P95，起点是前视开始写入应用缓存，终点是前视控件完成 Qt 绘制。第三行测于加入视角标签前，用于单独比较绘制路径。

| 刷新方式与控件 | 开始发布到提交给控件 | 开始发布到完成绘制 |
| --- | ---: | ---: |
| 16 ms 轮询，QLabel | 15.71 ms | 19.21 ms |
| 合并新帧通知，QLabel | 1.48 ms | 4.95 ms |
| 合并新帧通知，QWidget 直接绘制 | 0.81 ms | 2.01 ms |
| 完整界面，含常驻视角标签 | 1.75 ms | 3.78 ms |

立项时独立的四控件合成图对照测量了从提交四张图到四个控件都完成绘制的时间。三轮 P95 的中位数分别为 QLabel 配合 OpenCV 缩放 3.84 ms、自绘控件配合 OpenCV 缩放 1.99 ms、QPainter 直接缩放绘制 1.62 ms。两组测量的起止点不同。以上均为本机软件耗时。[历史四路回环基准](../benchmarks/results)
