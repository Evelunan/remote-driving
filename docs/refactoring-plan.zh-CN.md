# remote-driving-py 改造方案

编写日期：2026-11-16。代码基线：`65ec86e`。状态：待实施。

本方案覆盖驾驶端、车辆端、WebRTC 信令服务和 QUIC 中继服务，解决视频性能、重复代码、配置管理、独立部署和运行可靠性问题。

目标采用单仓库，默认划分为驾驶端、车辆端和统一服务端三个应用，将 WebRTC 信令与 QUIC 中继合并到服务端内部，抽取少量共享包。实施顺序为：修复控制正确性和失效保护，建立性能基线，优化视频与连接生命周期，再逐步迁移公共模块、配置和部署方式。

问题清单依据当前代码和隔离逻辑验证；视频耗时、网络条件与底盘行为尚需在目标设备上验证。文中的性能估算和架构建议不代表已经实现的结果。

## 1 改造目标和边界

| 目标 | 完成后的行为 |
| --- | --- |
| 控制正确且可失效保护 | 中立输入能到达车端；输入失效或控制超时后执行底盘定义的安全动作；重复、过期和越权指令不执行 |
| 视频延迟可解释 | 采集、编码、接收、显示分别计量；能识别旧画面和冻结；优化结果可重复比较 |
| 公共实现唯一 | 协议编解码、日志初始化、配置机制和连接生命周期有明确共享边界 |
| 配置真正生效 | 配置经过校验后由入口注入；单位明确；运行时可查看脱敏后的有效配置 |
| 应用独立交付 | 驾驶端、车辆端和统一服务端可分别构建、安装、启动和回退；服务端支持共同或分别启用信令与中继模块 |
| 故障可恢复 | 断线、设备拔出、重连和退出有明确状态及资源释放流程 |

首轮保留 WebRTC 视频、QUIC 控制和 PyQt GUI。媒体后端是否改用 GStreamer 或硬件编解码，由目标硬件上的基准测试决定。当前一车一驾驶的需求不要求引入 SFU、分布式消息系统或新的远程服务。

### 1.1 实施自主性和设计调整

本方案是实施基线。目录层级、模块划分、共享包数量、接口抽象和进程组织均可根据实际代码、测试和测量结果重新设计。发现现有或建议结构造成耦合、重复、资源浪费或维护困难时，可自主调整，不需要为了保持方案中的结构而保留不合理实现，也无需逐项确认常规、可逆的设计选择。

结构调整必须维持功能目标、控制失效保护、权限边界、协议兼容要求及可验证的验收条件。不得通过删减功能、弱化测试或把问题移出清单来宣告完成；文中已确认的问题若不再适用，需给出新实现消除该问题的依据。

实施中同步更新受影响的方案、部署说明和验收记录，说明调整原因、代码或测量依据、迁移影响及验证结果。安全阈值、底盘能力和真实部署条件仍以实际证据为准；自主设计不意味着可以假定尚未验证的实车参数。

### 2.2 连接生命周期和线程

| 编号 | 优先级 | 问题和证据 | 改造要求 |
| --- | --- | --- | --- |
| R01 | P1 | [驾驶端](../apps/driving/src/rd_driving/infrastructure/protocol/driving_protocol.py#L39) 和 [车辆端](../apps/vehicle/src/rd_vehicle/infrastructure/protocol/vehicle_protocol.py#L35) 在 UDP transport 建立时把基类私有 _connected 设为 True | 业务状态使用独立字段；连接就绪依赖正式握手事件及等待接口，避免绕过 TLS 握手等待 |
| R02 | P1 | 两端 HELLO 只经 Datagram 发送一次，没有应用确认 | 认证、注册和控制权协商使用可靠 stream 并等待响应；实时连续控制仍使用 Datagram |
| R03 | P1 | [中继清理](../apps/server/src/rd_server/relay/services/relay_protocol.py#L22) 依赖 connection_lost，却忽略单个 QUIC 连接的 ConnectionTerminated | 在连接终止事件中清理会话和心跳任务；关闭操作幂等 |
| R04 | P1 | [推流类](../apps/vehicle/src/rd_vehicle/infrastructure/streams/webrtc_streamer.py#L171) 第二次定义 close，覆盖前一个停止运行标志的实现 | 统一 shutdown，保存任务句柄，取消并等待任务结束，禁止关闭后自动重连 |
| R05 | P1 | [接收信令循环](../apps/driving/src/rd_driving/infrastructure/video/webrtc_reciver.py#L279) 捕获断线异常后继续读旧连接 | 断线结束当前 session，由外层退避重连；区分可恢复消息错误和连接失效 |
| R06 | P1 | [两端相同的 ICE 处理](../apps/vehicle/src/rd_vehicle/infrastructure/streams/peer_connection.py#L34) 使用 RTCIceCandidate(candidate=...)，不符合 aiortc API | 统一候选解析，或明确采用收集完成后的完整 SDP 交换；完整 SDP 路径可能掩盖此分支错误 |
| R07 | P1 | [控制线程](../apps/driving/src/rd_driving/infrastructure/workers/control_system_thread.py#L219) 调用 [主窗口绑定的 UI 回调](../apps/driving/src/rd_driving/main_window.py#L281) | 使用 Qt signal/slot 将界面更新交给 GUI 主线程 |
| R08 | P1 | [手动重连](../apps/driving/src/rd_driving/main_window.py#L288) 没有把旧服务停止完成作为新服务启动的条件，多处后台任务未记录句柄 | 用统一生命周期管理器按序停止和启动；避免阻塞 GUI 线程；旧会话回调不能污染新会话 |
| R09 | P2 | [创建 peer](../apps/vehicle/src/rd_vehicle/infrastructure/streams/webrtc_streamer.py#L82) 会 reset 全部共享轨道 | 采集源与订阅者生命周期分离；当前房间上限为两人，该问题主要影响多人扩展或重复建连 |

R01 与 R03 的行为已按 aioquic 1.3.0 官方实现核对。QUIC Datagram 不提供自动丢包重传；传输确认也不能代替应用注册成功。参考资料见第 10 节。

连接状态应拆为信令已连接、传输握手完成、会话已授权、首帧已到达、画面仍新鲜等状态。发送 answer 或启动线程都不应直接代表视频已可用。

## 3 视频性能改造

### 3.1 当前实际链路

```text
USB 摄像头采集线程
  → 请求 MJPG 采集并取得 BGR 图像（实际格式需确认）
  → 最新帧缓存
  → MultiCameraManager 发布
  → VideoFrameTrack 构造 VideoFrame
  → aiortc 编码和 WebRTC 传输
  → 驾驶端解码并转 BGR
  → FrameBuffer
  → CPU 缩放和 QPixmap 显示
```

[主窗口](../apps/driving/src/rd_driving/main_window.py#L169) 当前选择 MultiVideoWidget，OpenGL 分支被注释，车端 CUDA compositor 也未接入此链路。它们不应被当作当前已启用的加速能力或热点。应用层已有最新帧覆盖机制，应保留有界缓存，避免改成无界队列后积压旧画面。

### 3.2 先修可确认的无效工作

**提前判断帧版本。** 旧 UI 配置（`git show dd1d909:apps/driving/src/rd_driving/config/app.yaml`） 每 5ms 轮询；[MultiVideoWidget](../apps/driving/src/rd_driving/ui/widgets/multi_video_widget.py#L171) 先调用 [FrameBuffer.get](../apps/driving/src/rd_driving/infrastructure/video/frame_buffer.py#L48) 深复制图像，之后 [VideoDisplay](../apps/driving/src/rd_driving/ui/components/video_display.py#L254) 才丢弃重复帧。

按配置的一路 1080×720 和三路 640×480、BGR 每像素 3 字节、理论 200Hz 计算：

```text
(1080 × 720 + 3 × 640 × 480) × 3 × 200
= 1,019,520,000 字节/秒
≈ 1.02 GB/s 图像载荷复制量
```

该数字是估算，实际轮询频率、相机协商尺寸和内存流量需测量。改造时在复制前比较版本；或采用明确所有权的不可变帧引用。当前显示代码会原地绘制时间文字，应先改为显示覆盖层，才能安全减少复制。

**识别冻结和过期画面。** [推流循环](../apps/vehicle/src/rd_vehicle/application/multi_camera_manager.py#L69) 没有新帧时继续发布 pre_frame，[track](../apps/vehicle/src/rd_vehicle/infrastructure/streams/video_track.py#L31) 为旧图像生成新 PTS。因此接收 FPS 正常不代表摄像头正常。发布数据应保留采集序号、采集时间和源健康状态；重复发送用于保活时，不能把旧图像标成新采集。画面过期应明确提示，并按主视角失效策略联动控制。

**统一帧率和调度。** [采集线程](../apps/vehicle/src/rd_vehicle/infrastructure/cameras/usb_camera.py#L123) 有忙等，发布协程再次 sleep，track 又使用默认时基限帧。相机 FPS 没有传入 [track 创建](../apps/vehicle/src/rd_vehicle/infrastructure/streams/track_manager.py#L13)，且仅修改 _fps 不会自动改变基类 next_timestamp 的节奏。应以新帧事件驱动数据更新，用单调时钟组织发布和超时，明确采集帧率、发送帧率及显示刷新率。

**在实际编码位置管理资源。** MultiCameraManager 中的 semaphore 只保护更新最新帧引用和事件，没有包住 aiortc 编码任务。编码并发和线程预算应在实际后端测量后配置。高频图像转换、同步日志与设备写入也需要计入事件循环耗时。

B11 已实现只读帧快照、重复帧过滤及本地接收过期提示；缓存层固定负载复制量减少 85%，记录见 [视频性能测量](video-performance.zh-CN.md)。以上旧链路描述保留为问题依据。B12 已实现采集源与独立订阅、单调采集 PTS、相机目标 FPS、停止后不重发旧图像及推流关闭，真实回环双订阅验证通过；B13 已完成接收端生命周期与认证信令。B14 正式入口已统一控制/媒体及设备配置，移除旧加载器；完整媒体性能测量与进程隔离尚待完成。

### 3.3 用测量决定媒体后端

第一轮保留 aiortc，完成帧版本过滤、过期检测、调度和重连修复。若编码、解码或像素格式转换仍占主要成本，再在目标设备上对比原生媒体管线和硬件编解码。

硬件方案需要核对实际 codec、驱动、硬件编码器、像素格式、内存上传下载和解码显示路径。选择 H.264 不等于启用硬件编码；增加 GPU 拷贝也可能抵消收益。现有 OpenGL 分支还需要先修正 FrameBuffer 数据契约，不能直接取消注释就认定完成优化。

保留主视角与辅助视角分别配置分辨率、帧率和码率的能力。是否降辅助视角质量、是否车端合成，需结合可用上行带宽和驾驶视野要求评估。

### 3.4 性能基线和测量口径

每次基准记录硬件型号、系统与驱动、软件版本、相机实际协商参数、编码器、订阅者数量和网络条件。分别运行单路与四路、固定视频源与真实摄像头，保证改造前后的输入可比较。

| 指标 | 采集方法和用途 |
| --- | --- |
| 采集 编码 接收 显示 FPS | 各阶段独立计数；保留零值、重复帧和丢弃帧，定位掉帧阶段 |
| 各阶段耗时 P50 P95 P99 | 在处理边界记录本地单调时间，区分稳定开销与偶发卡顿 |
| CPU GPU RSS 和事件循环延迟 | 识别计算压力、内存增长及控制调度受影响程度 |
| 码率 丢包 抖动 RTT | 使用 aiortc getStats 及必要的补充埋点；记录直连或 TURN 等实际路径 |
| 画面年龄 冻结时长 首帧和重连时间 | 基于采集新鲜度及会话状态，判断视频是否可用于驾驶 |
| 控制采样至提交耗时 | 分别记录采样、发送、接收、控制器提交；真实执行延迟需要底盘反馈 |

跨主机的单调时钟不能直接相减。视频端到端延迟采用同一时钟画面或 LED 的拍摄测量，或者使用已校准的两端时钟并报告误差。QUIC echo RTT、RTT/2 都不能代替视频延迟或底盘执行延迟。

[现有统计脚本](../benchmarks/legacy/test_data_process.py#L63) 会去除 FPS=0，当前 FPS 写入代码也已注释。历史 CSV 可供回顾，但不作为当前版本的可靠基准。

## 4 应用结构和共享边界

### 4.1 单仓库和三个应用

驾驶端、车辆端和统一服务端保留各自的入口、依赖、配置与发布产物。现有 servers/webrtc 和 servers/quic 迁移为 server 应用内部的 signaling 和 relay 模块，默认共同部署。源码在同一仓库内演进，共享实现通过包依赖复用。

```text
remote-driving-py/
├── apps/
│   ├── driving/
│   │   ├── pyproject.toml
│   │   └── src/rd_driving/
│   ├── vehicle/
│   │   ├── pyproject.toml
│   │   └── src/rd_vehicle/
│   └── server/
│       ├── pyproject.toml
│       └── src/rd_server/
│           ├── main.py
│           ├── config.py
│           ├── auth/
│           ├── signaling/
│           └── relay/
├── packages/
│   ├── rd-core/src/rd_core/
│   ├── rd-webrtc/src/rd_webrtc/
│   └── rd-quic/src/rd_quic/
├── configs/examples/
├── deploy/
├── tests/
├── benchmarks/
├── docs/
└── pyproject.toml
```

这是默认目标结构，具体目录和模块可按第 1.1 节的原则调整，目录迁移应在行为测试建立后进行。各应用按需要保留 application、domain、adapters 等模块，只在有实际替换或测试需求的边界定义接口。

### 4.2 共享包的职责

默认按下表组织三个共享包；实施时可依据真实依赖与复用情况合并或拆分，保持依赖方向清晰，避免让轻量服务被迫安装 GUI、ROS 或视频引擎。

| 包 | 共享内容 | 边界 |
| --- | --- | --- |
| rd-core | 消息模型、枚举、版本、唯一 codec、序列号工具、配置加载与验证机制、日志初始化 | 不依赖 Qt、ROS、OpenCV 或媒体引擎；不包含底盘运动算法 |
| rd-webrtc | 信令消息和客户端、候选解析、连接状态、重连关闭、公共统计接口 | 车端采集与轨道策略留在 vehicle，驾驶端渲染留在 driving |
| rd-quic | 连接生命周期、认证注册确认机制、心跳、通用收发接口 | 中继路由留在 rd_server.relay，驾驶输入和车辆执行策略留在对应应用 |

依赖方向为应用指向共享包，rd-webrtc 和 rd-quic 可依赖 rd-core。应用不互相导入，共享包不反向依赖应用。控制运动计算从驾驶端 codec 中移出，并区分界面的目标值展示与车端实际执行。

### 4.3 服务端合并和运行边界

统一服务端拥有一个依赖声明、构建产物、配置入口和生命周期管理器，复用日志与身份认证机制。默认在一个进程内启动 WebSocket 信令监听和 QUIC 中继监听，同时保留独立协议模块、任务集合及连接清理逻辑。

以下为拟实现的命令接口，当前代码尚不支持：

```bash
rd-server --services signaling,relay
rd-server --services signaling
rd-server --services relay
```

不指定 services 时默认启用两项。单模块模式支持独立调试，并为未来按负载或故障隔离需求分进程部署保留入口；各模式使用同一个服务端制品。

合并后的边界如下：

| 边界 | 要求 |
| --- | --- |
| 协议监听 | 信令使用 WebSocket，生产使用 WSS；控制中继使用 QUIC。分别配置 TCP 与 UDP 监听端点，客户端继续分别配置两种连接 |
| 身份和授权 | 复用设备与操作员身份认证；视频房间管理订阅者，控制会话管理驾驶授权和独占控制租约。加入房间不自动获得控制权 |
| 会话状态 | 控制权由 relay 模块裁决。单模块分别运行时使用一致的令牌验证配置，不能依赖跨进程的内存单例；需要跨模块协作的状态通过明确接口交换 |
| 启动和就绪 | 所有选定模块成功启动后才报告就绪。任一必需监听启动失败时，关闭已启动的监听和任务并以失败状态退出 |
| 运行和关闭 | 单连接的非法消息在连接范围内处理。必需模块发生不可恢复故障时，撤销整体就绪状态并有序关闭，由进程守护重启；关闭后释放端口及后台任务 |
| 视频媒体 | 视频仍走车辆端与驾驶端之间的 WebRTC，必要时经过 TURN；合并不使信令模块或 QUIC 控制中继承载视频帧 |

同进程运行会让进程级故障同时影响两个模块，任务划分不能提供进程级隔离。现阶段合并主要降低维护和部署成本；负载或故障测试证明需要独立进程时，再使用单模块运行方式拆开部署。视频性能仍按第 3 节单独测量和优化。

### 4.4 车辆端进程隔离

[车端入口](../apps/vehicle/src/rd_vehicle/main.py#L117) 当前用同一事件循环运行控制和推流，只有摄像头采集使用线程。建议车辆应用内部提供 control 和 media 两个可独立启动、关闭和监控的进程，避免媒体工作拖慢控制调度。

本地通信只传必要的状态或最新控制快照，避免通过通用进程队列搬运大量原始图像。控制进程与底盘 watchdog 的超时检测不能依赖媒体进程。媒体崩溃、重启或画面过期时，按明确策略影响控制授权与运行状态。

若 ROS 绑定系统 Python，可进一步让 ROS bridge 使用该环境，媒体进程使用兼容的视频依赖环境；本地接口仍需版本和单位约定。进程隔离的额外资源开销纳入基准测试。

## 5 配置和日志方案

### 5.1 配置优先级和作用域

```text
内置默认值 < --config 指定的实例文件 < RD_* 环境变量 < CLI 参数
```

每个应用只加载当前角色需要的配置。入口完成合并、类型及语义校验后，将不可变配置传入组件，替换模块级加载单例。数组如 cameras 采用整体替换等明确规则，避免不同来源的隐式拼接。

| 配置归属 | 内容 |
| --- | --- |
| 驾驶端 | 输入设备与映射、UI 刷新、视频显示、服务连接参数 |
| 车辆端 | 相机和媒体参数、控制器类型、运动限值、输入与控制超时、服务连接参数 |
| 统一服务端公共配置 | 启用模块、身份认证、令牌验证、日志和整体生命周期策略 |
| 服务端 signaling 子配置 | WebSocket 监听地址、TLS 设置、房间容量、消息限制和视频订阅权限 |
| 服务端 relay 子配置 | QUIC 监听地址、TLS 文件位置、控制授权、会话和租约策略 |
| 共享机制 | 日志、配置合并、通用字段类型、消息与协议版本 |

同一部署环境的公共服务地址可以由部署模板生成到各实例配置。源码共享配置结构，部署实例拥有自己的值。运行中不热更新会影响控制行为的关键参数，除非后续定义了安全切换流程。

服务端默认使用一份实例配置，包含公共配置及 signaling、relay 两个子配置。单模块运行只要求所启用模块的必需字段，避免未启用模块的端口或证书缺失阻止启动；配置中的未知字段仍需报错。客户端的两个服务地址可以指向同一台机器，也支持分别部署的地址。

实施进展（B09）：服务端已采用上述机制，配置规范和可运行示例见[配置说明](configuration.zh-CN.md)。信令身份/房间授权以及 QUIC 服务端认证/租约已接入，协议见[控制协议 v2](control-protocol-v2.zh-CN.md)；客户端配置/新版协议迁移仍在实施中。

### 5.2 校验和配置可观测性

- 字段包含明确单位，例如 max_linear_mps、max_angular_radps、command_timeout_ms。
- 校验端口、正数帧率和超时、相机标识唯一性、控制器支持的字段、运动限值及编码器尺寸约束。
- 拒绝未知字段，错误指出字段路径；无效关键配置使启动失败，不静默切换到另一种控制器。
- 提供仅校验配置的命令模式，以及脱敏后的有效配置和来源信息；该模式不打开设备、不连接底盘。
- aiortc、aioquic 的配置对象由各适配器创建，配置模型不强制导入所有通信库。
- 认证令牌、TURN 凭据和私钥在部署时注入；日志和配置转储不输出秘密。

控制超时和画面过期阈值应由底盘制动能力、速度范围及网络基线决定。本方案不提供可直接用于实车的统一数值。

实施确认（2026-11-16）：用户选择 ROS2、Python 3.12；暂保留最大线速度 5.0 m/s、最大角速度 2.0 rad/s，并由配置控制。真实底盘停车/制动/超时能力暂不确定，先实现安全动作扩展接口和模拟验收，后续接入真实接口。软件中明确分开停车请求与停车确认；当前适配器发布零速目标时不得宣称底盘已经停车。

### 5.3 日志

应用入口调用一次日志初始化；模块只使用 logging.getLogger(__name__)。统一记录 service、vehicle_id、session_id 和连接代次，错误包含必要上下文。统一服务端额外记录 component，区分 signaling、relay 和 auth，同时使用统一的日志输出配置。

日志目录使用明确的运行路径，不依赖启动时 cwd。逐帧、逐控制采样改为调试采样或汇总指标，连接状态变化、授权变化和失效保护保留事件日志。根据测量结果使用有界异步日志队列，避免磁盘写入阻塞关键循环。

## 6 控制协议和安全状态

认证、注册、参数协商和控制权授予通过可靠 QUIC stream 完成，收到应用响应后才进入可控制状态。连续控制采样使用 Datagram，更新最新目标，不重放积压历史。离散动作使用有确认和幂等语义的独立消息。

建议协议明确以下字段和语义：

| 信息 | 目的 |
| --- | --- |
| protocol_version 和 message_type | 校验兼容性与消息结构 |
| 已授权会话和连接角色 | 服务端绑定身份，阻止自报身份越权 |
| session_epoch 和 control_seq | 区分重连及重启，拒绝重复和旧会话消息 |
| 输入新鲜度与控制有效期规则 | 防止发送端把过期输入不断包装成新包；定义接收后的失效期限 |
| CommandAck | 确认接收或明确约定的执行阶段，不冒充车辆实测 |
| VehicleTelemetry | 反馈真实测量、故障和控制器状态，注明来源及时间 |

车端 watchdog 以最后一条通过认证、会话、序列和内容检查的有效控制指令接收时间为依据，使用本地单调时钟。网络心跳、旧包、重复包和无效包均不能续期。针对网络滞留包的期限检查，还需要明确定义时钟同步或会话时效机制；单靠序号不能保证命令新鲜。

建议区分未授权、待控制、控制中、失效保护和故障状态。恢复连接不自动恢复旧目标；解除失效保护的条件由底盘策略明确。安全动作不简单等同于“所有数值置零”，应验证具体控制器的减速、停车、制动和保持能力。

协议增加字段时必须引入版本规则。可选方式是过渡期兼容两版，或安排驾驶端、车辆端和服务端协调升级；不兼容时明确拒绝建立控制会话，不能静默按错误格式解析。迁移期间也需验证旧信令和中继入口对应的协议版本。

## 7 打包和部署

驾驶端、车辆端和统一服务端分别声明依赖、构建后端、包资源和命令入口，发布 wheel 或按角色准备部署制品。服务端的两种协议能力由同一个制品交付，不再分别维护两套服务器依赖和发布流程。共享包随发布版本固定，远程机器通过安装制品获得依赖，不依赖跨目录导入或复制公共文件。

服务端迁移先保持现有信令与 QUIC 报文和监听端点兼容，再将旧配置映射到统一配置的对应子项。旧启动入口可短期保留为调用统一服务端单模块模式的兼容入口，双模块及单模块测试通过、部署说明切换完成后再删除。避免新旧进程同时占用同一监听端点；迁移与回退均需记录端口、证书位置和认证配置的对应关系。

现有 uv workspace 可用于兼容环境的统一开发。根项目没有依赖，普通 uv sync 不等于安装全部成员，应在开发说明中明确选择 --package 或 --all-packages。ROS 和其他不同 Python 环境分别进行依赖解析、安装及启动验证，不能仅以主开发环境通过为依据。

部署检查包括：

- 在干净环境安装制品，从仓库外的任意工作目录运行帮助、配置校验和模拟模式。
- 统一服务端验证双模块和两个单模块启动方式，以及部分启动失败后的回滚清理、整体就绪状态和端口释放。
- Linux 相机定位支持稳定设备路径，避免仅按可能变化的数字索引或无法区分同型号设备的 VID/PID。
- 底盘与相机的系统依赖、设备权限、动态库、ROS 环境和 Python 版本有明确说明。
- 每个进程有启动、停止、故障退出和重启策略；资源释放由程序完成，进程守护负责崩溃后的恢复。
- 保留上一版制品及对应配置；回退前检查协议和配置兼容性，车辆处于明确的安全状态。

## 8 分阶段实施和验收

每个阶段拆成可独立审查的小批次变更，功能修复、结构迁移和媒体后端替换分别交付。先有行为验证，再搬迁实现。阶段内可按依赖关系自主调整模块设计和实施顺序，保持问题清单、验收条件及设计调整记录同步。

| 阶段 | 主要交付 | 验收条件 |
| --- | --- | --- |
| 第一阶段 控制正确性和基线 | 修 C01–C10；建立模拟输入、模拟底盘和固定视频源；记录当前性能 | 路由正确；回中可达；旧包和重复包不执行；输入失效和设备阻塞时超时保护仍生效；配置限值和遥测语义正确；无权限连接不能控制 |
| 第二阶段 连接和视频缺陷 | 修 R01–R08；新帧过滤、冻结检测、统一帧率；管理后台任务及关闭流程 | 断线后可恢复；停止后不自行重连；冻结画面可识别；反复登录和重连后资源数量稳定 |
| 第三阶段 服务端合并和公共模块 | 唯一 codec、日志与配置机制；共享连接组件；三个应用的 src 布局；统一服务端入口及旧配置迁移 | 协议固定样本和边界测试通过；三个应用可分别构建安装；服务端双模块和单模块模式通过；部分启动失败可清理；身份认证统一且视频与控制权限独立 |
| 第四阶段 性能和进程隔离 | 按基准优化转换、复制和编码；控制与媒体分进程；必要时试验硬件后端 | 相同条件下报告改造前后 P50/P95/P99 与资源占用；媒体负载和崩溃不破坏控制失效保护 |
| 第五阶段 发布与持续回归 | 环境矩阵、CI、部署模板、兼容和回退流程、长时间测试 | 弱网、TURN、服务重启和设备失效场景通过；干净机器可部署；协议不兼容可识别；回退可复现 |

第一阶段认证或会话改动可能影响协议，应按第 6 节确定过渡方式。公共模块迁移尽量保持既有报文字节，避免把目录改造和协议变更混在一起。

### 8.1 必要回归场景

| 类别 | 场景和预期 |
| --- | --- |
| 协议 | 固定报文字节、长度和类型校验；重复、乱序、回绕、首包、发送端重启；错误会话和角色被拒绝 |
| 控制失效 | 回中、USB 拔出、驾驶端崩溃、链路黑洞、仅剩心跳、设备执行阻塞；有效控制超时后进入底盘定义的安全状态 |
| 状态语义 | 接收确认不表示执行成功；执行失败可见；无实测反馈时界面标注目标值 |
| 视频 | 单路和四路、拔相机、重复帧、冻结、分辨率及帧率切换、首次建连和重连 |
| 网络 | 局域网、强制 TURN、限速、延迟、抖动、丢包；记录路径及故障恢复时间 |
| 生命周期 | 连续登录退出、主动停止、信令重启、中继重启、旧会话晚到回调；检查任务、线程、socket 和 RSS 趋势 |
| 服务端合并 | 双模块和两个单模块模式；部分监听启动失败、必需模块不可恢复故障及整体重启；就绪状态准确、资源完整清理；拆进程时不依赖内存共享；视频订阅不授予驾驶权 |
| 配置和安装 | 未知字段、错误单位或范围、缺失必需值、多个配置实例、各目标 Python 环境和任意 cwd 启动 |

持续集成首先运行不依赖硬件的协议、配置、模拟控制和安装检查。硬件相关测试在目标设备执行，报告设备与网络条件。性能阈值根据第一阶段基线和实际驾驶要求制定，同时约束画面新鲜度、尾部延迟和控制调度。
