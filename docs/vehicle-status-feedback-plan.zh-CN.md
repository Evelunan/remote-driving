## 目标与字段约定

目标链路：底盘 ROS 状态 → 车辆端反馈适配 → 认证中继 → 驾驶端接收 → 界面显示。

以 `/vehicle_status` 的 `yunle_msgs/msg/VehicleStatus` 为反馈来源，回传以下全部字段：

| ROS 字段 | 含义 | 驾驶端展示位置 |
| --- | --- | --- |
| `cur_speed` | 底盘反馈车速 | 主界面 |
| `cur_steer` | 底盘反馈转向角 | 主界面 |
| `left_wheel_speed` | 左轮速度 | 诊断详情 |
| `right_wheel_speed` | 右轮速度 | 诊断详情 |
| `shift_level` | 底盘反馈档位 | 主界面 |
| `is_autodrive` | 自动驾驶使能状态 | 主界面 |
| `drive_mode` | 底盘驾驶模式 | 状态详情 |
| `p_status` | 底盘报告的刹车状态 | 主界面 |

单位与语义约定：

- 按用户要求，整车车速 `cur_speed` 暂按 **km/h 原值接收和显示**。这是一项实现假设，不代表已核实底盘 CAN 协议；不得因驱动注释不一致自行乘除 `3.6`。
- 左右轮速的源单位与整车车速分开配置、说明，在本项目的反馈适配层统一为 km/h；不得直接套用 `cur_speed` 的单位假设。
- 转向角以 **度（°）** 表示。车轮转向角与车身角速度分开建模，不将其填入现有 `angular_radps` 字段。
- 传输字段名称或协议说明明确单位，避免仅用无单位的 `speed` 表达不同量。
- `/cmd_vel` 的线速度 m/s 和角速度 rad/s 继续遵守现有接口约定；本功能不调整油门、制动、转向或换挡的控制逻辑。
- 档位、驾驶模式编码未确认前显示原始数值及未知说明，不猜测 D/R/N 等映射。
- 底盘反馈档位、刹车状态与驾驶外设本地输入分别展示。`p_status` 不单独构成车辆已停稳的证明，也不自动设置停车确认。

## 状态传递与有效性

- 新增独立的底盘状态消息，保留现有线速度/角速度遥测的语义；明确两端、服务端与共享包的版本匹配规则。
- 沿用现有认证、会话及租约约束，校验反馈来源、会话、代次、序号和采样新鲜度；状态反馈不续控制租约。
- 首版沿用现有控制会话回传，不另行扩展独立的只读监控通道。
- 记录原始消息时间和本地单调时钟接收时间，明确零值或无效时间戳的处理，不给重复发送的缓存样本刷新采样时间。
- 只发送新样本，限制回传频率，避免状态流阻塞控制指令、执行确认或窗口消息。
- ROS 回调与异步网络任务通过线程安全的最新状态快照交换数据，退出时回收订阅、执行器及相关任务。
- 保留字段有效性，个别轮速缺失或 NaN/Inf 时，不用零值替代，也不掩盖其他仍有效的状态。
- 未接入、无有效数据、反馈过期及连接断开时显示“未知/过期”；不得让旧状态继续表现为实时反馈。

## 分阶段开发与提交

以下每阶段均包含对应测试。阶段验证通过后立即提交，再开始下一阶段；测试不集中拖到最后补写。

| 阶段 | 实现内容 | 验证重点 | 计划提交 |
| --- | --- | --- | --- |
| 1. 状态协议 | 增加独立底盘状态消息，定义全部字段、单位、有效性和版本匹配规则 | 编解码往返、固定格式、非法数据、布尔与编码范围、无效字段和版本匹配 | `feat(protocol): add vehicle status messages` |
| 2. ROS 反馈采集 | 在车辆端订阅 `/vehicle_status`，实现字段映射、单位适配、时间记录、最新快照和资源退出 | 模拟 ROS 消息、全部字段映射、无效数据、采样时间、线程与退出行为 | `feat(vehicle): collect ROS chassis feedback` |
| 3. 状态回传 | 接通车辆端、中继和驾驶端，限制发送频率并处理会话及新鲜度校验 | 字段完整传递、来源与代次校验、重复与乱序、过期、断线和重连；状态不续租 | `feat(control): relay chassis status to driving client` |
| 4. 驾驶端显示 | 增加实际状态显示和诊断详情，区分外设输入与底盘反馈，显示未知及过期状态 | Qt offscreen 下的数值、单位、原始编码、布尔状态和反馈失效显示 | `feat(driving): display chassis feedback` |
| 5. 文档与验收 | 更新配置、依赖、协议、单位假设及人工验收说明，完成相关回归并记录结果 | 从模拟反馈到界面的完整链路、现有控制回归、文档与最终实现一致 | `docs(vehicle): document status feedback integration` |

实施时可以根据依赖关系细分提交，但每个提交应可检查、可验证；阶段范围变化时同步更新本文件。

## 测试隔离要求

- 单元测试使用普通数据对象和模拟 ROS 模块，不调用真实 `rclpy.init()`，不创建真实 ROS 节点，不发布真实 ROS 话题。
- 链路测试使用模拟控制器和测试中继。需要网络时，仅绑定 `127.0.0.1` 的动态端口，测试结束关闭所有监听器和任务。
- GUI 测试使用 Qt offscreen，避免连接真实驾驶外设或启动正式应用服务。
- 在项目内为本次测试分配独立目录，显式约束临时文件、运行目录及缓存位置；仅清理本次测试生成的文件。
- 使用现有项目环境，不修改系统环境；若缺少依赖，先记录问题，不向其他目录安装或同步依赖。
- 不执行修改网卡或路由的测试，不运行 `tc/netem`，不重启、停止或复用已有业务服务。
- 先运行与改动相关的测试，再运行已确认符合上述边界的回归；不直接执行未经检查的全量脚本。
- 软件模拟结果与实车结果分开记录；模拟通过不能写成实车已验收。

## 验收标准

1. 表中全部字段能从模拟底盘消息完整到达驾驶端，数值、单位和有效性符合约定。
2. 主界面可查看车速、转向角、反馈档位、自动驾驶使能和刹车状态；详情区可查看模式原始编码及左右轮速。
3. 首次无数据、无效数据、反馈中断、连接断开和重连时，界面状态明确且不沿用过期值。
4. 反馈链路不改变现有控制输入语义、指令时效、租约和停车确认逻辑，相关控制回归通过。
5. 软件测试的文件、进程和网络活动符合隔离要求，外部工作区及真实设备不受影响。
6. 代码和文档按阶段提交，并保留各阶段测试结果；实车验收步骤交由用户执行。
