# 设计补充

## 4.2.1 WebRTC信令服务器设计

**建议补充位置：** 放在“信令服务器整合了房间管理器……”这一段之后、图4-4之前。

信令服务器在设计上不直接参与视频媒体数据的传输，只负责连接建立前所需的信令交换。客户端接入后，服务器先为每个 WebSocket 连接分配唯一的对等体标识，并将其登记到全局对等体集合中；当客户端发送 `join` 消息时，房间管理器根据房间号创建或复用房间，并把该对等体加入房间。房间中最多保留两个对等体，用于对应一个车辆端和一个驾驶端，这样可以避免多个客户端进入同一房间后造成信令路由混乱。

房间生命周期由房间管理器统一维护。新的对等体加入房间时，服务器一方面向新加入者返回 `joined` 消息，使其获知自己在房间中的标识和已有成员；另一方面向房间内已有成员广播 `new_peer` 消息，使另一端能够及时发起或等待 WebRTC 协商。对于 `offer`、`answer` 和 `candidate` 等信令消息，服务器只根据消息中的目标对等体标识进行转发，不解析 SDP 和 ICE Candidate 的具体内容，从而保持信令服务的轻量化。

当 WebSocket 连接断开或客户端异常退出时，服务器会将该对等体从所在房间移除，并向房间中剩余成员发送 `peer_left` 消息。若房间内已经没有对等体，房间管理器会销毁该房间并释放对应的内存状态。通过这种方式，信令服务器能够支持车辆端和驾驶端的动态加入、离开与重连，同时避免失效连接长期占用房间资源。

## 4.2.2 QUIC中继服务器设计

**建议补充位置：** 放在“中继协议处理器即为自定义的中继转发服务……”这一段之后、图4-5之前。

QUIC 中继服务器以会话号作为车辆端与驾驶端的绑定依据。车辆端和驾驶端建立 QUIC 连接后，都会先发送 HELLO 类型报文，其中 `HELLO_CAR` 表示车辆端注册，`HELLO_DRIVING` 表示驾驶端注册。中继服务器解析报文头部中的消息类型和 `session` 字段后，将当前 QUIC 协议对象登记到会话管理器中，形成 `session -> car/driving` 的映射关系。后续数据转发不依赖客户端 IP 地址，而是依赖会话号和角色信息，因此更适合客户端重连或部署环境变化的场景。

控制链路采用 QUIC Datagram 传输。服务器收到 `CONTROL` 或 `STATE` 报文后，只解析报文头部判断来源角色，再根据会话号查找对端连接并转发完整报文。这样做可以减少服务器侧处理开销，也能保持控制报文本身在驾驶端、车辆端之间的一致性。若当前会话中尚未找到对端连接，服务器直接丢弃该报文并记录状态，避免将控制指令转发到错误对象。

为保证控制链路的可用性，中继服务器在连接建立后启动周期性心跳探测任务，向已绑定会话的客户端发送 `HEARTBEAT` 报文。客户端自身也会定期发送心跳，用于维持链路状态。连接断开时，中继服务器通过会话管理器移除该协议对象对应的绑定关系；若某个会话下的车辆端和驾驶端都已离线，则删除整个会话状态。该设计使中继服务既能完成低延迟转发，又能在断线后及时清理会话。

## 4.3.2 视频接收模块设计

**建议补充位置：** 放在“WebRTC接收器整合信令客户端……”这一段之后、图4-7之前。

驾驶端视频接收模块采用状态驱动的设计方式。接收器启动后先进入信令连接状态，连接成功后发送 `join` 消息加入指定房间；若房间中没有车辆端，则进入等待状态；当收到 `new_peer` 或 `offer` 消息后，模块转入 WebRTC 协商阶段。收到车辆端的 SDP Offer 后，驾驶端创建本地 PeerConnection，设置远端描述，生成 SDP Answer 并通过信令服务器返回给车辆端。ICE Candidate 的交换在连接建立过程中持续进行，用于补充双方可用的网络路径。

视频帧到达时，PeerConnection 会触发 `track` 事件。每一路视频轨道单独启动接收任务，持续调用 `track.recv()` 获取解码后的媒体帧，并将其转换为 OpenCV 常用的 BGR 图像格式。不同摄像头通过轨道标识进行区分，例如前、后、左、右视角分别写入对应的帧缓冲位置。这样界面层不需要关心 WebRTC 连接细节，只需要按视角读取最新帧即可。

帧缓冲区采用“只保留最新帧”的策略。对于远程驾驶场景，过期视频帧的价值较低，如果按顺序堆积显示，反而会增加驾驶员看到画面的延迟。因此系统在每一路视频中只保存最新一帧，并通过线程锁保证写入和读取的一致性。界面刷新时读取当前最新帧进行绘制，能够在网络抖动或短时间解码不稳定时减少画面滞后。

## 4.3.3 控制指令采集发送模块设计

**建议补充位置：** 放在“发送阶段是整个过程的消费者……”这一段之后。

控制指令链路采用原始数据队列和处理后数据队列分离的方式。采集阶段只负责读取 USB 外设产生的原始字节数据，并尽快写入原始队列；处理阶段从原始队列中取出数据，解析方向盘、油门和制动等字段，并转换为统一的归一化控制量；发送阶段再从处理后队列中读取控制量并封装为二进制控制报文。三个阶段之间通过队列解耦，可以避免 USB 读取、数据解析和网络发送互相阻塞。

发送模块在建立 QUIC 连接后先发送 `HELLO_DRIVING` 报文完成身份注册，随后进入控制循环。控制循环以固定节奏读取处理后的控制量并发送 `CONTROL` 报文，系统当前设计的发送间隔约为 20 ms，对应 50 Hz 控制频率。该频率能够满足驾驶操作的连续性要求，同时不会过度占用控制链路带宽。

车辆端执行控制指令后，会把当前控制量以 `STATE` 报文形式回传给驾驶端。驾驶端根据报文中的时间戳计算往返时延，并将线速度、角速度和传输延迟反馈到界面。这样控制链路不仅用于下发驾驶指令，也承担了基本的状态反馈功能，便于驾驶员判断车辆是否仍处于可控状态。

## 4.3.4 用户界面设计

**建议补充位置：** 放在“主控制页面包括视频显示区……”这一段之后。

驾驶端界面采用页面栈管理登录页面和控制页面。系统启动时只显示登录页面，驾驶员输入 WebRTC 房间号和 QUIC 会话号后，主窗口再创建控制页面，并同时启动视频接收线程和控制系统线程。这种设计可以把会话参数和后台服务启动绑定在一起，避免在未选择车辆或会话时提前建立网络连接。

控制页面中的视频显示、连接状态和车辆状态由不同后台任务提供数据。视频接收线程负责维护 WebRTC 接收器，并将收到的视频帧写入帧缓冲区；控制系统线程负责 USB 外设、控制数据处理和 QUIC 通信；主线程通过 Qt 定时器定期刷新视频画面和统计信息。后台线程不直接操作界面组件，而是通过 Qt 信号或回调把状态变化传递给主线程，从而保证界面更新的线程安全。

界面退出和重新登录时，需要先停止视频接收线程、控制线程以及各类定时器，再销毁控制页面。这样可以避免旧会话的 WebRTC 连接、QUIC 连接或 USB 读取任务继续运行，影响下一次登录后的连接状态。对远程驾驶系统而言，清晰的启动和退出流程有助于减少调试过程中的残留连接，也能提高实际使用时的稳定性。

## 4.4.2 多路视频采集与管理设计

**建议补充位置：** 放在“多路视频管理组件……实现多路视频的采集与管理”这一段之后。

车辆端多路视频采集采用单摄像头独立采集、多路统一调度的结构。每个摄像头对象负责自身的设备初始化、帧率控制和最新帧缓存，多路视频管理组件负责启动所有摄像头，并为每个摄像头创建独立的推流任务。摄像头启动后预留短暂预热时间，使自动曝光和驱动缓冲趋于稳定，再开始向推流模块提供图像帧。

在推流调度过程中，多路视频管理组件不会要求每次循环都必须读取到新帧，而是通过帧计数判断摄像头是否产生了新画面。如果某一路摄像头短时间没有产生新帧，系统继续使用上一帧或初始黑帧进行推流，避免单路摄像头异常导致整个视频链路阻塞。不同摄像头之间互不等待，能够提升多路采集的稳定性。

考虑到多路视频同时编码可能造成 CPU 瞬时占用过高，管理组件设计了推流并发限制。当前通过异步信号量限制同时进入推流操作的摄像头数量，使四路视频在保证实时性的同时减少资源竞争。这种设计适合车辆端计算资源有限的场景，也便于后续根据硬件性能调整并发数量、分辨率和帧率。

## 4.4.3 视频推流模块设计

**建议补充位置：** 放在“WebRTC 推流器整合了信令客户端……”这一段之后。

车辆端推流模块使用视频轨道管理器维护多路 WebRTC 视频轨道。系统启动时，多路摄像头管理组件先按照摄像头名称注册轨道名称；当需要与驾驶端建立 PeerConnection 时，轨道管理器根据已注册名称创建对应的 `VideoStreamTrack`，并将这些轨道加入同一个点对点连接。每一路轨道内部只保存最新视频帧，WebRTC 发送端在需要编码时从轨道中取出最新帧并封装为媒体帧。

在连接建立流程上，车辆端承担主动发起 Offer 的角色。当车辆端发现房间内已有驾驶端，或收到驾驶端加入房间的通知后，会创建 PeerConnection、添加视频轨道、生成 SDP Offer，并通过信令服务器发送给驾驶端。驾驶端返回 SDP Answer 后，车辆端设置远端描述，并继续交换 ICE Candidate，最终完成媒体连接建立。

推流模块还需要处理信令断开和对端离开的情况。每次重新连接信令服务器后，推流器会清理旧的 PeerConnection，并重新创建视频轨道，避免旧轨道状态影响新的连接。当收到 `peer_left` 消息时，系统关闭对应的 PeerConnection 并移除该对等体记录，等待驾驶端重新加入后再次发起协商。

## 4.4.4 控制指令接收与执行设计

**建议补充位置：** 放在“车辆控制器负责接收转向、加速、制动等控制量……”这一段之后。

车辆端控制指令接收模块在 QUIC 连接建立后发送 `HELLO_CAR` 报文，将自身注册到指定会话中。收到中继服务器转发的 `CONTROL` 报文后，模块会先完成二进制解码，提取消息类型、会话号、序列号、时间戳以及油门、制动、转向控制量。为了避免乱序或重复报文造成车辆执行旧指令，车辆端根据 `seq` 字段判断报文新旧，只处理比上一条更新的控制指令。

指令通过校验后，车辆端会将原始控制量封装为 `STATE` 报文回传给驾驶端。该报文沿用驾驶端发送时的时间戳和序列号，因此驾驶端可以根据回传时间计算控制链路往返时延，也可以在界面上显示车辆端接收到的控制状态。对于远程驾驶闭环而言，这一状态回传可以帮助驾驶员判断控制链路是否仍然稳定。

控制执行部分采用控制器抽象接口。车辆端业务逻辑只调用统一的 `send_command(throttle, brake, steering)` 方法，不直接依赖具体底盘类型。实际部署时可以选择串口控制器，将控制量转换为底盘控制板可识别的串口帧；也可以选择 ROS2 控制器，将控制量转换为 `Twist` 消息并发布到 `/cmd_vel` 话题。通过这种抽象，系统能够在测试模式、串口小车和 ROS2 平台之间切换，而不需要修改控制链路的主体逻辑。
