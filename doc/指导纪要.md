# 毕业设计指导纪要

> **课题名称**：基于 WebRTC 与 QUIC 协议的远程驾驶系统设计与实现

---

## 第1次指导纪要

**指导时间**：2025年11月中旬

### 一、上次指导至本次指导期间学生做了哪些工作

1. 查阅了远程驾驶、遥操作领域的相关文献资料，了解了国内外远程驾驶技术的研究现状与发展趋势，重点关注了 5G 远程驾驶、基于 WebRTC 的远程监控系统等方向的代表性工作。
2. 调研了 WebRTC、QUIC 等实时通信协议的基本原理与应用场景，初步了解了 WebRTC 的 ICE/STUN/TURN 穿透机制和 QUIC 协议的 0-RTT 快速握手等核心特性。
3. 分析了当前自动驾驶技术的局限性，了解到远程遥操作作为人机协同方案在智能交通、无人配送、矿山作业等场景中的实际应用需求。
4. 初步确定了毕业设计的选题方向——基于视频流的低延迟远程驾驶系统，并梳理了系统需要解决的核心技术挑战：低延迟视频传输和可靠控制指令传输。

### 二、要求指导教师本次指导或答疑的问题

1. 关于选题范围界定：远程驾驶系统涉及视频采集、编码传输、控制指令通信、底盘控制等多个环节，我不确定应重点聚焦哪些核心环节，整体开发范围是否需要进一步缩小？
2. 关于技术路线可行性：使用 Python 作为开发语言是否能满足远程驾驶场景对极低延迟的实时性要求？系统的整体实现难度对于本科毕业设计的工作量是否合适？
3. 关于硬件需求：开发和测试本原型系统是否必须依赖实际的物理车辆平台和多路摄像头设备？

### 三、指导教师指导或答疑的内容及要求

1. 肯定了选题方向的创新性与工程价值，指出远程驾驶是自动驾驶的重要补充方案，具有明确的应用前景。建议将系统定位为原型验证系统，聚焦于视频传输与控制指令传输两条核心链路的设计与实现。
2. 关于技术可行性，指出 Python 生态中已有成熟的 WebRTC（aiortc）和 QUIC（aioquic）库，结合 asyncio 异步编程模型可以满足实时性要求；系统复杂度适合本科毕业设计。
3. 硬件方面，建议使用树莓派等嵌入式设备模拟车辆端，配合 USB 摄像头和 USB 驾驶模拟器（方向盘+踏板）即可完成开发测试，不需要实际车辆。
4. 建议进一步阅读 WebRTC 与 QUIC 协议的相关 RFC 文档，明确两种协议在远程驾驶场景中各自的优势与适用范围。
5. 要求学生撰写开题报告初稿，明确研究背景、研究目标与技术路线，下次指导时进行讨论。

## 第2次指导纪要

**指导时间**：2025年12月初

### 一、上次指导至本次指导期间学生做了哪些工作

1. 完成了开题报告初稿的撰写，详细论述了研究背景与意义、国内外研究现状综述、研究内容与目标等章节，并梳理了系统的核心需求。
2. 深入学习了 WebRTC 协议栈（包括 ICE/STUN/TURN 穿透机制、SDP 协商流程、RTP/RTCP 传输机制）和 QUIC 协议（0-RTT 握手、Datagram 扩展 RFC 9221）的技术细节及其在低延迟场景的应用优势。
3. 调研了 Python 生态中的异步网络编程框架，测试了 aiortc（WebRTC）和 aioquic（QUIC）两个核心依赖库的 API 与基本使用方式，并确认了它们与 asyncio 的兼容性。

### 二、要求指导教师本次指导或答疑的问题

1. 关于系统通信架构的设计：考虑到视频数据（高带宽）和控制指令（高频率）的特性差异，我不太确定在整体架构划分时，视频传输和控制指令传输是应该复用同一条通信链路，还是分开处理？
2. 关于网络拓扑结构：驾驶端和车辆端通常处于不同的局域网内，系统的整体网络拓扑应该如何设计才能保证两端稳定、低延迟的连接？

### 三、指导教师指导或答疑的内容及要求

1. 明确了系统通信架构的方案：由于视频数据（高带宽、容忍偶尔丢帧）与控制指令（低带宽、高频、要求极低延迟）在传输特征上存在根本差异，指导采用**双通道并行方案**进行解耦传输。
2. 针对双通道的技术选型给出了建议：视频链路选用 WebRTC，主要利用其 ICE 框架的 P2P 直连能力和内置的自适应编解码机制以降低延迟；控制链路选用 QUIC Datagram，利用其无重传等待的特性避免 TCP 队头阻塞，保障 50Hz 控制指令的实时性。
3. 针对网络拓扑问题，建议采用"车辆端—服务器—驾驶端"三层分布式架构，通过在云端部署信令服务器与中继服务器来解决跨局域网的连接问题。
4. 要求进一步完善开题报告中的技术路线部分，根据上述讨论画出系统总体架构草图，为后续的系统代码开发奠定基础。

### 二、要求指导教师本次指导或答疑的问题

1. 关于代码架构与组织结构：系统涉及驾驶端、车辆端和两类服务器（WebRTC 信令、QUIC 中继），应该采用怎样的代码目录组织结构来统一管理这些复杂的子系统？
2. 关于模块间的耦合问题：为了保证系统未来的可扩展性（例如更换不同的摄像头或底盘设备），各端内部的业务逻辑和底层硬件接口应该如何设计才能实现真正的松耦合？

1. 针对各端内部的代码结构，建议统一采用四层架构设计（硬件接口层、通信层、业务层、展示/应用层），严格遵循依赖倒置原则，确保上层业务不直接依赖底层具体实现。
2. 针对硬件解耦问题，建议通过引入抽象接口（如 ICamera、IController）来隔离具体硬件。使得后续适配不同类型的摄像头或底盘控制协议（如串口、ROS2）时，无需修改核心的控制和推流逻辑。
3. 针对整体项目的组织结构，建议采用 monorepo 工程管理模式，使用 Python 的 uv workspace 将驾驶端、车辆端、两类服务器作为独立的子项目进行统一维护和依赖管理。
4. 要求学生本周内完成项目代码工程框架的搭建与初始化，并在下次汇报时展示项目的基本目录结构与依赖配置。
