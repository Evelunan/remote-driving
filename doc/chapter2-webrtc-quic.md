# 第2章 相关技术与理论

## 2.1 WebRTC

WebRTC（Web Real-Time Communication）是一种用于实时音视频通信的技术。它最早由 Google 推出，后来逐渐由 W3C 和 IETF 推进标准化。和普通的视频文件传输不同，WebRTC 更强调实时性，要求音视频在采集、编码、传输、解码和播放之间尽量减少等待时间。远程驾驶系统中，驾驶员需要根据车辆端摄像头传回的画面判断车辆周围环境，如果视频延迟过大，驾驶员看到的就不是车辆当前状态，而是已经滞后的状态。因此，本文在视频链路中选择 WebRTC，主要是考虑到它在低延迟音视频传输、网络穿透和传输质量自适应等方面已有比较成熟的支持[17]。

WebRTC 不是单独的某一个协议，而是由多种协议和模块共同组成。一个 WebRTC 连接建立起来之前，双方一般需要先通过信令服务器交换协商信息，再收集和交换网络候选地址，之后通过 ICE 进行连通性检测，最后才开始传输媒体数据。也就是说，WebRTC 实际上包含了会话协商、连接建立、媒体传输、传输反馈和安全保护等多个部分。对于应用开发者来说，WebRTC 已经封装了很多底层通信细节，但在使用时仍然需要理解这些过程，否则在处理连接失败、视频卡顿或网络切换等问题时会比较困难。

信令是 WebRTC 建立连接的第一步。WebRTC 标准并没有规定信令服务器必须使用哪一种协议实现，也没有规定信令消息必须按照固定业务格式组织[17]。开发者可以根据系统需要使用 WebSocket、HTTP 或其他方式转发信令消息。在本系统中，信令服务器主要负责车辆端和驾驶端之间的连接协商，包括房间加入、SDP Offer/Answer 转发、ICE Candidate 转发以及连接断开后的清理等。这样设计的好处是，WebRTC 只负责媒体通道本身，系统业务中关于车辆、驾驶端、房间和会话的管理则由应用层完成。

WebRTC 的会话协商通常使用 SDP（Session Description Protocol）完成。SDP 用文本形式描述本端支持的媒体能力和传输参数，其中会包含媒体类型、媒体方向、编解码器、RTP 参数、加密信息以及 ICE 相关字段等内容。例如，媒体类型可以表示本次协商中传输的是音频、视频还是数据；媒体方向可以表示某一端是发送、接收还是双向传输；编解码器信息用于说明本端支持哪些视频编码格式；ICE 用户名片段、ICE 密码和候选地址则用于后续的网络连通性检测。虽然这些字段在实际代码中一般由 WebRTC 库自动生成，但它们决定了两端最终能否正确建立媒体通道。

SDP 协商一般采用 Offer/Answer 模型。发起连接的一端先生成 Offer，描述自己希望建立的媒体会话；另一端收到 Offer 后，根据自身支持的能力生成 Answer。双方完成 Offer 和 Answer 交换后，就可以确定本次连接中使用的媒体方向、编码格式和传输参数。在本文系统中，车辆端主要负责发送摄像头视频，因此需要在协商中声明视频轨道和编码能力；驾驶端主要负责接收和显示视频，因此需要根据协商结果建立视频接收通道。如果系统同时传输前方、后方、左侧和右侧等多路视频，还需要区分不同的视频轨道，避免驾驶端显示时混淆画面来源。

在网络环境比较简单时，两端可以直接通过局域网地址或公网地址通信。但远程驾驶系统通常不是这种理想情况。车辆端和驾驶端可能位于不同局域网，也可能经过 NAT、路由器或防火墙。此时，如果只依靠本机地址，两端往往无法直接连接。WebRTC 使用 ICE（Interactive Connectivity Establishment）来处理这类问题。ICE 会让双方收集不同类型的候选地址，然后逐一进行连通性检测，最后选择能够通信的路径。

常见的 ICE 候选地址主要包括主机候选地址、服务器反射候选地址和中继候选地址。主机候选地址来自本机网卡，一般适用于同一局域网内通信。服务器反射候选地址通常由 STUN 服务器帮助获得，它反映了终端经过 NAT 后在公网侧表现出来的地址。中继候选地址则来自 TURN 服务器，当两端无法直接建立连接时，可以由 TURN 服务器转发媒体数据。STUN 本身并不持续转发视频数据，它更多是帮助终端发现可用地址；TURN 则会实际参与转发，因此可以提高连接成功率，但也会增加服务器带宽消耗和一定的传输延迟。

对远程驾驶系统来说，P2P 连接和中继连接各有作用。如果能够建立 P2P 连接，视频数据可以直接从车辆端到驾驶端，路径更短，延迟通常也更低。如果网络条件复杂，P2P 无法建立，则需要依靠 TURN 中继来保证连接可用。远程驾驶不能只追求最低延迟，也要考虑实际网络环境下连接能否建立。因此，在设计视频链路时，应优先使用直接连接，同时保留中继方案作为补充。这样即使部分网络环境不利于穿透，系统仍有机会维持基本的视频传输。

媒体传输方面，WebRTC 主要使用 RTP/RTCP。RTP 用于传输音视频媒体数据，每个 RTP 包中带有序列号、时间戳和同步源标识等字段[18]。序列号可以帮助接收端判断数据包顺序和丢包情况，时间戳用于视频帧的播放同步，同步源标识则用于区分不同媒体源。实时视频传输和文件传输不同，文件传输要求内容完整，而实时视频更看重数据是否及时到达。如果某一帧很晚才到达，即使数据本身没有错误，也可能已经没有播放价值。因此，RTP 更适合按时间顺序组织媒体数据，让接收端在较短缓冲时间内完成播放。

RTCP 主要用于传输质量反馈。接收端可以通过 RTCP 向发送端反馈丢包率、抖动、接收统计和往返时延等信息。发送端根据这些反馈判断当前网络状态，并调整视频发送策略。例如，当网络出现拥塞时，可以降低码率或分辨率，减少网络压力；当网络状况较好时，可以适当提高画质。远程驾驶系统中，多路摄像头会同时占用带宽，如果始终以固定高码率发送，在网络变差时很容易造成排队和卡顿。WebRTC 的自适应传输可以在画质和实时性之间做一定平衡。对驾驶场景来说，在一些情况下，保持画面连续比保持最高画质更重要。

WebRTC 还对媒体传输安全作了要求。音视频流一般通过 SRTP（Secure Real-time Transport Protocol）进行加密，密钥协商则与 DTLS 等机制配合完成[18]。远程驾驶的视频画面包含车辆周围环境、道路情况以及车辆运行状态，如果这些数据在传输过程中被窃听或篡改，会影响系统安全。使用 WebRTC 时，媒体加密属于协议默认考虑的内容，应用层不需要再从零设计一套视频加密方案，这也降低了系统实现难度。

在本文系统中，WebRTC 主要用于车辆端多路摄像头视频回传。车辆端采集摄像头画面后，将其作为视频轨道发送到驾驶端；驾驶端收到视频流后进行解码，并在界面中显示前方、后方、左侧和右侧等不同视角。这样可以为驾驶员提供比较完整的环境感知信息。WebRTC 对多路媒体轨道的支持，使每一路摄像头可以相对独立地管理，也便于驾驶端根据轨道信息安排界面布局。

不过，WebRTC 并不能解决所有问题。多路视频同时传输会明显增加带宽和编码压力，如果车辆端性能不足，可能出现帧率下降；如果网络带宽不足，多路视频之间可能互相影响，导致画质下降或延迟增加。WebRTC 的拥塞控制可以缓解这些问题，但不能突破设备性能和网络带宽的限制。因此，在实际系统中仍需要合理设置摄像头分辨率、帧率和编码参数，并在驾驶端界面中显示视频状态。当某一路摄像头异常或帧率明显下降时，驾驶员应能及时发现，而不是完全依赖底层协议自动处理。

因此，本文将 WebRTC 用于视频链路，是因为它比较符合远程驾驶对实时视频传输的要求。它能够完成会话协商、NAT 穿透、媒体传输、质量反馈和安全保护等工作，减少了自行设计视频传输协议的复杂度。同时，WebRTC 在网络波动时可以根据反馈调整发送策略，这对于多路视频传输也有一定帮助。虽然它仍然受到带宽和硬件性能限制，但作为车辆端到驾驶端的视频传输方案，能够满足本文系统的基本需求。

## 2.2 QUIC协议

QUIC（Quick UDP Internet Connections）是一种基于 UDP 的传输层协议，最初由 Google 提出，后来由 IETF 标准化为 RFC 9000[19]。它在 UDP 的基础上实现连接管理、拥塞控制、多路复用、安全加密和丢包恢复等功能。本文系统中的控制指令链路数据量不大，但发送频率较高，对延迟比较敏感。如果控制指令传输不及时，车辆端执行的动作就会落后于驾驶员当前操作，影响远程驾驶的控制体验。因此，本文选择 QUIC 作为控制链路的基础协议，并使用 QUIC Datagram 传输高频控制报文。

QUIC 基于 UDP 构建，主要是为了摆脱传统 TCP 在一些场景中的限制。TCP 提供可靠、有序的字节流传输，这对文件下载和网页加载等场景很合适，但对实时控制不一定完全合适。因为 TCP 中某些数据丢失后，后续数据可能需要等待重传完成才能继续交付，这会造成队头阻塞。远程驾驶控制指令更关心当前最新状态，而不是每一条历史指令都必须恢复。QUIC 在 UDP 之上重新实现了连接和传输控制逻辑，可以在保留连接管理和拥塞控制的同时，提供比传统 TCP 更灵活的传输方式。

连接建立是 QUIC 的一个重要特点。传统的 TCP 加 TLS 通信通常要先完成 TCP 三次握手，再完成 TLS 握手，连接建立阶段会消耗多个往返时延。QUIC 将传输连接建立和 TLS 1.3 握手结合在一起，首次连接通常可以在 1-RTT 内完成，在满足条件时还可以支持 0-RTT 数据发送[20]。1-RTT 表示双方经过一个往返时延后即可开始安全传输，0-RTT 则主要用于已有连接信息的恢复场景。对于远程驾驶来说，如果控制链路发生短暂中断，连接恢复时间越短，系统越容易尽快回到可控状态。当然，在实际使用 0-RTT 时还需要考虑安全和重放风险，不能只看连接速度。

QUIC 的安全性来自其对 TLS 1.3 的集成。它不是先建立一个普通传输连接，再在应用层外加加密，而是把密钥协商、传输参数协商和数据加密放在协议流程中一起完成[20]。远程驾驶控制指令会直接影响车辆运动，如果指令被伪造或篡改，后果会比较严重。因此，控制链路必须考虑传输安全。QUIC 内置加密可以为控制报文提供基本保护，也减少了应用层自己设计加密封装时可能出现的错误。

多路复用也是 QUIC 的主要特性之一。TCP 把一个连接中的数据看作连续字节流，如果前面的数据缺失，后面的数据即使已经到达，也可能无法及时交付给应用层。QUIC 可以在同一连接中建立多个独立的数据流，不同流之间的阻塞影响相对较小[19]。在本文系统当前实现中，控制链路主要传输控制报文和车辆状态信息，数据类型并不复杂。但从扩展角度看，QUIC 的多路复用可以为以后增加诊断信息、告警信息或其他车辆状态数据提供方便，不必为每类小数据都建立新的连接。

QUIC 还使用连接 ID 来标识连接。传统 TCP 连接依赖源 IP、目的 IP、源端口和目的端口组成的四元组，一旦网络地址发生变化，连接往往会断开。QUIC 通过连接 ID 维护连接状态，当终端 IP 或端口变化时，只要连接 ID 仍然有效，就有可能继续使用原来的连接[19]。车辆端在实际运行中可能遇到无线网络波动、网络出口变化等情况，连接迁移能力对这类场景有一定意义。虽然本文测试环境相对固定，但从系统后续扩展看，这一特性有助于提高移动网络环境下的适应性。

在拥塞控制方面，QUIC 会根据确认信息、丢包情况和 RTT 估计结果调整发送速率。发送过快可能导致网络排队，发送过慢又可能影响控制频率，因此控制链路也需要合适的发送节奏。QUIC 运行在 UDP 之上，很多实现可以在用户态调整拥塞控制策略，例如使用 CUBIC 或 BBR 等算法[19]。对于远程驾驶控制报文来说，拥塞控制的目标不是追求很高吞吐量，而是尽量保持稳定、低延迟的传输。

远程驾驶控制指令和普通可靠数据传输有明显区别。文件传输要求内容完整，少一个字节都可能导致文件不可用；而控制指令是连续更新的状态量，例如方向盘角度、油门开度和制动力度会不断变化。某一条旧指令如果丢失，下一条指令很快就会携带新的控制状态。此时再重传旧指令，不一定有意义，甚至可能因为到达太晚而干扰当前控制。也就是说，在控制链路中，“一定送达”并不总是最重要的，“及时送达最新数据”反而更符合实际需求。

如果使用完全可靠的流式传输，当网络发生丢包时，发送端会进行重传，接收端也可能等待缺失的数据。以 50Hz 控制频率为例，相邻两次控制报文间隔约为 20ms。如果某一条报文丢失，下一条报文很快就会产生。如果系统仍然等待旧报文重传，车辆端接收到的控制状态就可能落后于驾驶员当前操作。对于远程驾驶来说，这种延迟积累会影响操控的跟手感，也可能带来安全风险。因此，控制链路并不适合简单照搬普通可靠传输思路。

QUIC Datagram 正是为这类实时数据提供的一种传输方式。它允许在 QUIC 连接上发送不可靠数据报，数据报不保证一定到达，也不要求按序交付，丢失后不会等待重传[22]。但它和普通 UDP 又不完全一样，因为它仍然使用 QUIC 连接中的加密、拥塞控制和连接管理。这样既避免了可靠流传输中旧数据阻塞新数据的问题，又保留了 QUIC 在安全和连接管理方面的优点。因此，QUIC Datagram 比较适合传输高频、小数据量、实时性要求高的控制报文。

在本文系统中，驾驶端会持续读取方向盘、油门和制动等外设数据，并将其转换为归一化控制量。之后，系统把这些控制量封装为二进制控制报文，通过 QUIC Datagram 发送到服务器，再由服务器转发给车辆端。控制报文中可以包含消息类型、会话标识、序列号、时间戳和控制量等字段。消息类型用于区分控制报文、状态报文和心跳报文；会话标识用于区分不同远程驾驶会话；序列号可以帮助判断报文是否乱序或丢失；时间戳可以用于计算往返时延，也可以帮助判断报文是否过期；控制量则保存车辆端需要执行的转向、速度、油门或制动信息。

由于 QUIC Datagram 不保证可靠到达，应用层仍然需要做必要的保护。车辆端收到控制报文后，应优先执行最新的有效报文。如果某个报文序列号明显落后，或者时间戳显示它已经过期，就不应该继续执行。除此之外，车辆端还需要设置超时检测。如果一段时间内没有收到新的有效控制报文，系统应认为控制链路可能异常，并触发减速、制动或安全停车等保护逻辑。这样可以避免车辆在失去远程控制后继续按照旧指令运行。

本文没有把控制指令直接放在 WebRTC DataChannel 中传输，而是单独使用 QUIC 链路，主要是为了让视频链路和控制链路相互独立。视频传输关注带宽、画质和画面连续性，控制传输关注低延迟和最新状态，两者的数据特点并不相同。如果把控制指令和视频都放在同一套通信链路中，一旦视频链路出现较大波动，控制指令也可能受到影响。分离之后，即使视频画质下降或帧率波动，控制报文仍可以通过独立的 QUIC 链路发送；反过来，控制链路中的高频小报文也不会干扰视频媒体传输。

因此，QUIC 在本文系统中主要承担控制链路的传输任务。它的快速握手、TLS 1.3 加密、多路复用、连接 ID 和连接迁移等特性，为控制通信提供了基础；QUIC Datagram 则进一步满足了控制报文对低延迟和最新状态传递的要求。结合序列号、时间戳和超时保护等应用层设计后，QUIC Datagram 可以较好地支撑远程驾驶中的高频控制指令传输。

## 2.3 本章小结

本章主要介绍了本文系统中用到的 WebRTC 和 QUIC 两项通信技术。WebRTC 主要用于视频链路，它通过信令协商、SDP、ICE、STUN/TURN、RTP/RTCP 和安全传输等机制，支持车辆端视频流传输到驾驶端。对于远程驾驶来说，WebRTC 的意义在于降低视频传输延迟，并在网络条件变化时尽量保持画面可用。

QUIC 主要用于控制链路。它基于 UDP 实现连接管理、安全加密、拥塞控制和多路复用等功能，而 QUIC Datagram 又可以在不等待重传的情况下发送实时控制报文。由于远程驾驶控制指令更重视最新状态而不是历史报文的完整恢复，因此这种方式比普通可靠流传输更适合本文系统。

通过本章分析可以看出，WebRTC 和 QUIC 分别对应远程驾驶系统中的视频感知和控制指令传输。前者解决“看得及时”的问题，后者解决“控制得及时”的问题。后续章节将在这些技术基础上，进一步分析系统需求，并设计车辆端、驾驶端和服务器端的具体模块。
