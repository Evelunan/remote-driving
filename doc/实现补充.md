# 实现补充

## 5.2.1 WebRTC信令服务器实现

**建议补充位置：** 放在“WebRTC信令服务器基于websockets库实现……”这一段之后。

信令服务器入口由 `SignalingServer` 类负责。服务启动时读取配置中的监听地址、端口、心跳间隔、超时时间和最大消息长度，并调用 `websockets.serve()` 创建 WebSocket 服务。每当车辆端或驾驶端建立连接时，服务器会调用房间管理器注册一个新的 `Peer` 对象，并为该连接进入独立的异步消息循环。消息循环持续读取客户端发来的 JSON 字符串，再交给 `RoomManager.handle_message()` 处理。

`RoomManager` 内部维护两个核心字典：一个保存所有房间对象，另一个保存所有在线对等体对象。收到 `join` 消息时，房间管理器根据房间号创建或复用 `Room`，并检查房间是否已经达到最大人数限制。客户端成功加入后，服务器先向原有成员广播 `new_peer`，再向新成员发送 `joined`，其中包含当前客户端的标识和房间中已有成员列表。这样车辆端和驾驶端能够根据对方是否已经在线决定后续连接流程。

对于 `offer`、`answer` 和 `candidate` 消息，房间管理器不解析其具体内容，只补充缺失的 `from` 字段，并按照 `to` 字段定向转发；如果没有指定有效目标，则向房间内除发送者以外的成员广播。连接关闭时，`unregister_peer()` 会调用离开房间逻辑，从房间中移除该对等体，广播 `peer_left`，并在房间为空时删除房间对象。这一实现使信令服务器保持较少业务状态，主要承担房间管理和消息路由职责。

## 5.2.2 QUIC中继服务器实现

**建议补充位置：** 放在“QUIC中继服务器使用aioquic库实现……”这一段之后。

QUIC 中继服务器的数据处理逻辑主要由 `RelayProtocol` 完成。该类继承 `aioquic.asyncio.QuicConnectionProtocol`，在 `quic_event_received()` 中只处理 `DatagramFrameReceived` 事件。收到数据报后，服务器先调用 `ControlCodec.decode_header()` 解析报文头部，得到消息类型和会话号，再根据消息类型进入身份绑定、数据转发或心跳处理流程。

`SessionManager` 用于保存会话绑定关系。其内部使用 `session_id -> {"car": protocol, "driving": protocol}` 的结构记录每个会话下的车辆端和驾驶端连接，同时使用 `protocol -> session_id` 的反向索引辅助断线清理。当服务器收到 `HELLO_CAR` 或 `HELLO_DRIVING` 时，会根据 `ControlCodec.get_role()` 得到角色名称，并将当前协议对象绑定到对应会话中。连接丢失时，`connection_lost()` 会调用 `unbind()` 删除该连接对应的绑定关系。

控制数据转发采用 Datagram 原样转发方式。服务器收到 `CONTROL` 或 `STATE` 报文后，根据报文来源角色查找同一会话下的对端协议对象，如果找到则调用对端的 `_send_datagram()` 将完整字节数据发送出去；如果未找到对端，服务器记录丢弃日志并结束处理。`RelayProtocol` 在连接建立后还会创建心跳检测任务，每隔固定时间向已绑定会话的客户端发送 `HEARTBEAT` 报文，用于维持链路并发现异常连接。

## 5.3.1-5.3.2 驾驶外设与控制发送实现

**建议补充位置：** 放在“该模块通过设备的厂商标识……”这一段之后，可作为 5.3.1 的补充。

驾驶端控制系统由 `ControlSystemThread` 统一启动和管理。该线程继承 `QThread`，在线程内部创建独立的 asyncio 事件循环，并并发运行 USB 采集、数据处理、QUIC 通信和状态处理四类任务。USB 采集任务通过工厂创建 USB 设备对象，并把读取到的原始数据写入原始队列；数据处理任务从原始队列取出数据，经解析和归一化后写入处理后队列。由于采集和处理通过队列连接，USB 读取的阻塞或短暂异常不会直接阻塞网络发送任务。

**建议补充位置：** 放在“在完成与服务器的QUIC连接建立后……”这一段之后，可作为 5.3.2 的补充。

控制指令发送由 `DrivingProtocol` 实现。QUIC 连接建立后，协议对象先调用 `_send_hello()` 发送 `HELLO_DRIVING` 报文，随后启动业务循环。业务循环通过 `asyncio.wait_for()` 从处理后队列中获取控制量，避免在队列暂时为空时永久阻塞；拿到数据后，调用 `ControlCodec.encode()` 将油门、制动和转向归一化值编码为二进制报文，并通过 QUIC Datagram 发送。发送后任务短暂休眠 0.02 秒，使控制发送频率保持在约 50 Hz。

`DrivingProtocol` 同时处理车辆端回传的 `STATE` 报文。收到 Datagram 后，协议对象调用 `ControlCodec.decode()` 解析报文，如果消息类型为 `STATE`，则把消息交给状态队列或界面回调。`ControlSystemThread` 的状态处理任务进一步根据时间戳计算 RTT，并结合最大线速度、最大角速度估算车辆当前运动状态，最终将线速度、角速度和延迟显示到控制面板中。

## 5.3.3 WebRTC 视频接收实现

**建议补充位置：** 放在“在服务启动阶段，接收模块使用信令客户端连接信令服务器……”这一段之后。

`WebRTCReceiver` 是驾驶端视频接收流程的核心封装。它内部保存信令客户端、对等连接管理器集合、当前客户端标识、视频帧回调和状态回调。`start()` 方法采用循环重连结构：先连接信令服务器，再清理旧的 PeerConnection 状态，注册 `joined`、`offer`、`candidate`、`peer_left` 和 `new_peer` 等消息处理函数，最后发送 `join` 消息加入房间并进入信令监听循环。若信令连接异常断开，模块等待短暂时间后重新连接。

收到车辆端发送的 `offer` 后，接收器创建新的 `PeerConnectionManager`，将车辆端 SDP 设置为远端描述，再创建本地 Answer 并通过信令服务器发送回车辆端。对等连接创建时，模块注册 `track` 事件回调；当视频轨道到达后，为每一路轨道创建独立异步任务，不断调用 `track.recv()` 获取视频帧。帧对象随后被转换为 `bgr24` 格式的 ndarray，并通过 `on_frame()` 注册的回调写入 `FrameBuffer`。

`FrameBuffer` 固定维护 `front`、`back`、`left`、`right` 四个位置的帧对象。每次写入时根据 track id 定位对应视角，并递增帧编号；读取时返回帧副本，避免界面绘制过程中与接收线程写入同一数组产生冲突。该缓存结构较简单，但符合远程驾驶的实时显示需求：界面始终读取最新帧，而不是等待旧帧逐个显示。

## 5.3.4 GUI界面实现

**建议补充位置：** 放在“在系统启动阶段，主窗口（MainWindow）加载登录页面……”这一段之后。

主窗口 `MainWindow` 使用 `QStackedWidget` 管理登录页面和控制页面。用户登录成功后，主窗口保存 `session_id` 和 `room`，创建导航栏、多路视频组件和右侧控制面板，然后调用 `_start_services()` 启动后台服务。视频服务通过 `WebRTCReceiverThread` 运行 WebRTC 接收器，接收器收到帧后写入共享的 `FrameBuffer`；控制服务通过 `ControlSystemThread` 运行 USB 采集、数据处理和 QUIC 通信。

界面刷新由多个 Qt 定时器驱动。帧刷新定时器定期触发多路视频组件更新，使视频显示区从 `FrameBuffer` 读取最新画面；统计定时器读取各视频窗口的帧率和分辨率，并更新控制面板中的摄像头信息；时间定时器更新底部状态栏时间。连接状态变化则通过 `SignalBridge` 和视频接收线程信号传递给主线程，由主线程统一更新控制面板中的信令、WebRTC、视频流、USB 和 QUIC 状态。

退出登录或关闭窗口时，主窗口会先设置服务停止标志，然后停止帧刷新、统计和时间定时器，再依次请求视频接收线程和控制系统线程退出，并等待线程结束。旧控制页面被销毁后再重新创建空页面，保证下一次登录时不会复用旧会话的组件引用。该处理避免了后台线程继续访问已销毁界面控件的问题。

## 5.4.1 多路视频采集实现

**建议补充位置：** 放在“在单路视频采集中，系统使用opencv打开摄像头设备……”这一段之后。

`USBCamera` 在初始化时根据操作系统选择 OpenCV 的摄像头打开方式，在 Linux 下使用 V4L2 后端，在其他系统下使用默认后端。摄像头打开后，程序将 OpenCV 内部缓冲区大小设置为 1，并设置 MJPG 编码格式，以减少驱动层缓存和高分辨率传输压力。随后根据配置写入分辨率和帧率，并记录实际生效的宽、高和 FPS。

摄像头采集在独立守护线程中运行。采集循环根据目标帧率计算下一帧时间，采用睡眠加短暂忙等的方式控制采集节奏；到达采集时间后，先调用 `grab()` 获取最新帧，再调用 `retrieve()` 解码为图像。相比直接使用 `read()`，这种方式更便于控制采集时间点，也有利于减少缓冲区中旧帧造成的延迟。每次成功获取图像后，线程在锁保护下更新 `_latest_frame` 和 `_frame_count`。

`MultiCameraManager` 负责多路摄像头统一启动和推流调度。启动阶段会并发启动所有摄像头，并等待约 3 秒预热时间；随后为每个摄像头创建 `_camera_push_worker()` 任务。推流任务通过帧计数判断是否产生新帧，并在无新帧时复用上一帧。为避免多路视频同时编码导致 CPU 峰值过高，管理器使用异步信号量限制同时推流的摄像头数量。

## 5.4.2 视频推流模块实现

**建议补充位置：** 放在“视频推流模块基于aiortc库实现……”这一段之后。

车辆端视频轨道由 `TrackManager` 和 `VideoFrameTrack` 配合实现。`TrackManager` 先保存已注册的摄像头名称，在建立新的 PeerConnection 前调用 `reset_tracks()` 关闭旧轨道并重新创建轨道对象。`VideoFrameTrack` 继承自 aiortc 的 `VideoStreamTrack`，内部保存最新 ndarray 图像和一个异步事件；摄像头推流任务调用 `update_frame()` 更新最新帧，WebRTC 编码端调用 `recv()` 取出最新帧并转换为 `av.VideoFrame`。

`WebRTCStreamer` 启动后会连接信令服务器、注册信令处理函数并加入房间。当收到 `joined` 或 `new_peer` 消息，且房间内存在驾驶端时，推流器创建 `PeerConnectionManager`，从轨道管理器中取出所有视频轨道并加入连接，然后创建 SDP Offer 发送给驾驶端。收到 `answer` 后，推流器设置远端描述；收到 `candidate` 后，继续补充 ICE 候选地址，直到点对点媒体链路建立。

在运行过程中，`WebRTCStreamer` 保存 peer id 到 PeerConnection 的映射，用于支持对端离开和重连。信令连接重建时，模块会关闭旧连接并清空 peer 集合；收到 `peer_left` 消息时，也会关闭对应连接并删除记录。这样可以避免旧 PeerConnection 持续占用视频轨道或网络资源。

## 5.4.3 控制指令接收与执行实现

**建议补充位置：** 放在“VehicleProtocol该类继承于aioquic中的QuicConnectionProtocol……”这一段之后。

车辆端 QUIC 客户端由 `VehicleDatagram` 负责启动。该类根据配置创建 `QuicConfiguration`，开启 Datagram 支持，并设置证书校验、最大 Datagram 大小和空闲超时时间等参数。`start()` 方法采用持续重连结构：连接失败或连接关闭后，等待固定时间再次连接中继服务器。连接建立后，客户端创建 `VehicleProtocol` 实例，等待 QUIC 握手完成，再启动车辆端业务循环。

`VehicleProtocol` 启动后先发送 `HELLO_CAR` 报文完成车辆端身份注册，然后进入心跳循环，定期发送 `HEARTBEAT` 维持连接。控制报文通过 `DatagramFrameReceived` 事件进入 `_handle_datagram()`，由 `ControlCodec.decode()` 解析为字典结构。若消息类型为 `CONTROL`，协议对象调用 `process_control_message()` 处理；若为心跳报文，则只记录连接状态。

在控制处理函数中，车辆端先读取 `seq` 字段，并通过 `ControlCodec.is_newer()` 判断当前报文是否比上一条更新。重复或乱序的旧报文会被直接丢弃，避免车辆执行过期控制。对于有效报文，车辆端提取油门、制动和转向值，先构造 `STATE` 报文回传给驾驶端，用于 RTT 计算和状态显示，再调用具体控制器下发到底盘。

底盘控制器通过统一接口接入。`SerialController` 根据车辆配置中的最大线速度、最大角速度和串口通信模板，将控制量转换为底盘控制帧，填充速度、转向方向和校验位后通过串口写出；`RCLpyCmdVelController` 则将控制量转换为 ROS2 `Twist` 消息，发布到 `/cmd_vel` 话题。车辆端主程序根据配置选择 `none`、`serial` 或 `ros2` 控制器，因此同一套 QUIC 接收逻辑可以用于测试模式、串口底盘和 ROS2 平台。
